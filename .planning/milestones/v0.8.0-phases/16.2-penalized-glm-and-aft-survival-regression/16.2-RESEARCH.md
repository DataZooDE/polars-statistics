## Summary

anofox-regression 0.5.16 adds exactly two new modules — `solvers::penalized_glm` and
`solvers::aft` — confirmed by reading `src/lib.rs`'s prelude (8 new names, zero
collisions with existing polars-statistics imports) and by diffing every `pub` item
against 0.5.15 (Phase 16.1's COVERAGE.md already did this and deferred both modules
here). Both new modules are **family-generic single engines**, a different shape from
every existing GLM in this codebase: instead of six separate Rust regressor types
(`PoissonRegressor`, `BinomialRegressor`, …), `PenalizedGlmRegressor` takes a
`PenalizedGlmFamily` enum value and dispatches internally; `AftRegressor` takes an
`AftDistribution` enum value. This is a real, if small, architectural choice for the
Python surface: **one PyModel class per engine** (`PenalizedGLM`, `AFT`), each taking a
`family=`/`distribution=` string parameter, is the natural mapping — not six/four
separate classes mirroring the existing per-family pattern — because the roadmap's own
success criteria read "Penalized GLM is exposed as **a** PyModel (family:
poisson/binomial/...)" (singular), and the Rust type itself is singular.

Both engines are used through the **same entry point this codebase already uses for
every other GLM**: `XxxRegressor::builder()....build().fit(&x_mat, &y_col)`, confirmed
by reading `py_negative_binomial.rs`, `py_tweedie.rs`, and the `*_fit`/`*_summary_fit`
functions in `regression.rs` — every one of them builds its own faer `Mat`/`Col` from
Polars `Series` and calls the builder/`.fit()` entry point. The crate's own
column-major `fit_poisson`/`fit_aft` free functions are explicitly documented
upstream as "what a SQL / FFI front end calls" and are **not used anywhere in this
codebase** for any existing GLM — skip them for both the PyModel and expression
layers; building the faer `Mat`/`Col` directly (as `build_xy_data` already does) and
calling the builder is the established, lower-risk pattern.

The one genuinely new wiring problem is **priors**: no existing polars-statistics
expression accepts a list/struct-shaped argument — every current kwarg is a scalar
literal (`pl.lit(x, dtype=...)`) passed through `args=`. Reading
`python/polars.plugins.register_plugin_function`'s actual docstring this session
confirms the answer already exists in the library: the function accepts a **separate**
`kwargs: dict[str, Any]` parameter that is JSON-serialized Python-side and
deserialized Rust-side via the exact `#[derive(Deserialize)] struct PredictKwargs`
mechanism already used for `prefix` on every `*_predict` expression (`output_type_func_with_kwargs=`).
A `priors: list[dict]` and `vcov_type: str` belong there, not in `args=`. `offset` is
different again — it is **per-row data**, so it must be a real expression input
column; the simplest correct default for "no offset" is a broadcast `pl.lit(0.0)`
column (adding zero to the linear predictor is mathematically a no-op for every link
function the engine supports), avoiding any `Option<Col<f64>>` plumbing at the FFI
boundary entirely.

R reference values for **both** new engines ship inside the published
`anofox-regression` 0.5.16 crate itself — `tests/fixtures/penalized_glm_aft_reference.rs`
(523 lines of `pub const` arrays, generated by `tests/r_scripts/penalized_glm_aft_reference.R`
from R 4.6.1 / MASS 7.3.65 / survival 3.8.6) is present in the crates.io package as
extracted into the local cargo registry cache — no separate git checkout or R
installation is needed to get exact reference numbers for 6 GLM configurations
(Poisson×3 links, Binomial×3 links + Logistic, Gamma, Tweedie, NegBin free/fixed
theta, Poisson+offset, Poisson+priors×3 vcov types) and 4 AFT distributions
(Weibull/LogNormal/LogLogistic/Exponential), each with coefficients, SEs,
deviance/log-likelihood/AIC, and (for AFT) quantile predictions. `tests/r_validation_penalized_glm_aft.rs`
is the upstream test that consumes this fixture and shows the exact tolerance
convention (relative error, `1e-5`..`1e-7` depending on quantity) to copy into pytest.

Mann-Whitney/Wilcoxon (UPST-07) is a much smaller, independent task: the upstream
`MannWhitneyResult`/`WilcoxonResult` structs already carry `estimate: Option<f64>` and
`conf_int: Option<ConfidenceInterval{lower,upper,conf_level}>` (confirmed by reading
`anofox-statistics-0.4.6/src/nonparametric/wilcoxon.rs:38-75`) and the `PyMannWhitneyU`/
`PyWilcoxonSignedRank` PyModel classes already expose both as getters. Only the
**expression** layer (`mann_whitney_u_fit`/`wilcoxon_signed_rank_fit` in
`nonparametric.rs`, using `generic_stats_output`/`stats_output_dtype`) is missing
them — a straightforward three-field-additive change to a dedicated new output dtype,
with one hazard: **Phase 16.1 Plan 09 adds a test that locks the *current*
2-field schema as a deliberate "unchanged in 16.1" assertion**
(`tests/test_wilcoxon_mcnemar_parity.py::...expression_schema`). This phase must find
and update that specific test when it lands (see Common Pitfalls).

**Primary recommendation:** Two new PyModel classes (`PenalizedGLM`, `AFT`) each
wrapping the crate's single family-generic engine via a `family=`/`distribution=`
string parameter, using the existing `builder()...build().fit(&x, &y)` entry point
exactly as every other GLM in this codebase does; new `#[polars_expr]` fit/summary/
predict expressions per engine (not per family) using the `kwargs=` JSON channel for
priors/vcov_type and a zero-literal default for offset; and a 3-field additive
extension to the Mann-Whitney/Wilcoxon expression output dtype, with an explicit task
to locate and update 16.1 Plan 09's schema-lock test.

## Entry-Point Decision (Research Question 1)

Both new engines expose **two** entry points per the module doc comments
(`[VERIFIED: anofox-regression-0.5.16/src/solvers/penalized_glm/mod.rs:1-58, src/solvers/aft/mod.rs:1-29]`):

1. **Builder** — `PenalizedGlmRegressor::builder().family(..).priors(..).vcov_type(..).offset(..).compute_inference(..).build().fit(&x: &Mat<f64>, &y: &Col<f64>)`; `AftRegressor::builder().distribution(..).compute_inference(..).build().fit(&x, &time, &event: &[bool])`.
2. **Column-major free functions** — `fit_poisson(y: &[f64], x: &[Vec<f64>], &PoissonOptions) -> GlmResult` (one per family) and `fit_aft(time: &[f64], x: &[Vec<f64>], event: &[f64], &AftOptions) -> AftResult`. The module doc explicitly calls these "what a SQL / FFI front end calls."

**Decision: use the builder for both the PyModel and the expression layer.** Evidence:
`grep -c "fit_poisson\|fit_binomial\|fit_negbinomial\|fit_gamma\|fit_tweedie\|fit_logistic" src/` across the whole polars-statistics tree returns zero hits today — every existing GLM (`negative_binomial_fit`, `tweedie_fit`, `poisson_fit`, …, in `regression.rs`, and every `py_*.rs` GLM wrapper) calls `XxxRegressor::builder()...build().fit(&x, &y)` on a `faer::Mat`/`Col` it assembles itself from `Series` via `build_xy_data`/`ToFaer`. Using the column-major functions here would be the **first** departure from that pattern in the codebase for no benefit (the builder already accepts the same column-major-origin data once converted to `Mat`/`Col`, which this codebase already knows how to do). The AFT builder additionally takes `event: &[bool]`, matching a straightforward `Series.bool()?.into_no_null_iter().collect()` conversion.

## New Upstream API — Penalized GLM (`anofox-regression::solvers::penalized_glm`)

All signatures `[VERIFIED: anofox-regression-0.5.16 source read this session — regressor.rs, types.rs, families.rs, mod.rs]`.

### `PenalizedGlmFamily` (enum, `Copy`)
```rust
pub enum PenalizedGlmFamily {
    Poisson(PoissonLink),              // ::poisson() = log link
    Binomial(BinomialLink),            // ::binomial() = logit link
    Logistic { threshold: f64 },       // ::logistic() = threshold 0.5
    NegativeBinomial { theta: Option<f64> },  // ::negative_binomial() = theta estimated (MASS::glm.nb)
    Gamma,                              // ::gamma() = log link
    Tweedie { power: f64 },             // ::tweedie(power), 1 <= power <= 2
}
```
`PoissonLink` ∈ {Log, Identity, Sqrt}; `BinomialLink` ∈ {Logit, Probit, Cloglog} — both already imported in `regression.rs` from `anofox_regression::core`/`LinkFunction` for the existing non-penalized GLMs, so no new link-parsing helper is needed beyond extending `parse_*` patterns already in the file.

### `PenalizedGlmRegressorBuilder` (builder methods, all confirmed)
```
.family(PenalizedGlmFamily)            // default Poisson(Log)
.with_intercept(bool)                  // default true
.max_iterations(u32)                   // default 100
.tolerance(f64)                        // default 1e-8
.compute_inference(bool)               // default false
.confidence_level(f64)                 // default 0.95
.lambda(f64)                           // uniform ridge on non-intercept coefficients; composes additively with priors
.priors(Vec<PriorSpec>)                // p or p+1 entries (leading = intercept); empty = none
.vcov_type(VcovType)                   // default Laplace
.offset(Col<f64>)                      // added to linear predictor on the link scale; None = no offset
.build() -> PenalizedGlmRegressor
```

### `PriorSpec` / `PriorKind` / `VcovType`
```rust
pub enum PriorKind { Flat, Normal, Laplace }
pub struct PriorSpec { pub kind: PriorKind, pub loc: f64, pub scale: f64 }
impl PriorSpec {
    pub fn flat() -> Self;
    pub fn normal(loc: f64, scale: f64) -> Self;
    pub fn laplace(loc: f64, scale: f64) -> Self;
}
pub enum VcovType { Laplace /* default */, Sandwich, Naive }
```
Laplace priors switch the inner solve to proximal coordinate descent (per-module doc);
`VcovType` controls which covariance is reported, independent of which prior kind was
used.

### `FittedPenalizedGlm` (accessors, all confirmed, `[VERIFIED: regressor.rs:368-490]`)
```
.coefficients() -> &Col<f64>            // NaN for columns dropped as constant/aliased
.intercept() -> Option<f64>

.pseudo_r_squared() -> f64

```
**No `predict_with_interval`** exists on `FittedPenalizedGlm` (unlike the pre-existing
`FittedNegativeBinomial`/`FittedTweedie` etc., which do) — a predict expression for
this engine can only return point predictions, not a confidence/prediction interval.

### `GlmInferenceResult` (`[VERIFIED: types.rs:408-445]`)
```rust
pub struct GlmInferenceResult {
    pub std_errors: Vec<f64>,
    pub z_values: Vec<f64>,
    pub p_values: Vec<f64>,
    pub ci_lower: Vec<f64>,
    pub ci_upper: Vec<f64>,
    pub confidence_level: f64,
    pub vcov: Option<Mat<f64>>,
    pub information: Option<Mat<f64>>,
    pub matrix_parameters: Vec<Option<usize>>,  // None=intercept row, Some(j)=feature j
}
```
This has **CI fields** (`ci_lower`/`ci_upper`) that the existing shared
`summary_output_dtype`/`summary_output()` helper (term/estimate/std_error/statistic/
p_value, 5 fields, used by every other GLM's `*_summary_fit`) does **not** carry.
Reusing the shared helper would silently drop `ci_lower`/`ci_upper` from "full
coverage." Recommend a **new**, dedicated `penalized_glm_summary_output_dtype`
(7 fields: term/estimate/std_error/statistic/p_value/ci_lower/ci_upper) rather than
modifying the shared one used by ~10 other `*_summary_fit` functions (the CONTEXT's
"additive only, no reshaping of existing signatures" principle applies here by
extension even though CONTEXT only named Mann-Whitney/Wilcoxon explicitly).

### Column-major entry points (NOT used — see Entry-Point Decision)
`fit_poisson`/`fit_binomial`/`fit_logistic`/`fit_negbinomial`/`fit_gamma`/`fit_tweedie`,
each `(y: &[f64], x: &[Vec<f64>], options: &XxxOptions) -> GlmEngineResult<GlmResult>`
(for `fit_logistic`, `GlmEngineResult<LogisticResult>` with an extra `.accuracy` field).
Each per-family `XxxOptions` struct duplicates `fit_intercept`/`max_iterations`/
`tolerance`/`compute_inference`/`confidence_level`/`lambda`/`prior_opts:
GlmPriorOptions`/`offset_column: Option<usize>` (1-based index into `x`) —
confirmed field-for-field identical shape across `PoissonOptions`/`BinomialOptions`/
`NegBinomialOptions`/`TweedieOptions`/`GammaOptions`/`LogisticOptions`
`[VERIFIED: types.rs:136-379]`. Not needed given the builder decision above, but useful
context: it confirms `GlmPriorOptions{priors: Vec<PriorSpec>, vcov: VcovType}` is the
one place priors/vcov_type are threaded through regardless of entry point.

## New Upstream API — AFT (`anofox-regression::solvers::aft`)

All signatures `[VERIFIED: anofox-regression-0.5.16 source read this session — regressor.rs, model.rs, distribution.rs]`.

### `AftDistribution` (enum, `Copy`)
```rust
pub enum AftDistribution { Weibull, LogNormal, LogLogistic, Exponential }
```
`from_name(&str) -> Option<Self>` accepts case-insensitive `"weibull"`,
`"lognormal"`/`"log_normal"`/`"log-normal"`, `"loglogistic"`/`"log_logistic"`/
`"log-logistic"`, `"exponential"`/`"exp"` — use this directly for Python-string
parsing rather than hand-rolling a match (it is `pub`, re-exported at the module
root). `scale_is_fixed()` is `true` only for `Exponential` (sigma fixed at 1, not
estimated — one fewer free parameter, and `log_scale_std_error` is `None` for it).

### `AftRegressorBuilder`
```
.distribution(AftDistribution)         // default Weibull
.with_intercept(bool)                  // default true
.max_iterations(u32)                   // default 100
.tolerance(f64)                        // default 1e-9
.compute_inference(bool)               // default false
.confidence_level(f64)                 // default 0.95
.priors(Vec<PriorSpec>)                // same PriorSpec type as penalized GLM (re-exported from penalized_glm)
.vcov_type(VcovType)                   // same VcovType as penalized GLM
.build() -> AftRegressor
```
`AftRegressor::fit(&self, x: &Mat<f64>, time: &Col<f64>, event: &[bool]) -> GlmEngineResult<FittedAft>`
— **no `offset`** on AFT's builder (confirmed absent; only penalized GLM has offsets).
`time` must be strictly positive; `event[i] == true` = observed, `false` = right-censored.

### `FittedAft` (accessors, `[VERIFIED: regressor.rs:120-212]`)
```
.coefficients() -> &Col<f64>            // log-time scale
.intercept() -> Option<f64>
.scale() -> f64                         // sigma; 1.0 for Exponential
.distribution() -> AftDistribution
.log_likelihood() -> f64
.null_log_likelihood() -> f64           // intercept(+scale)-only model, for LR pseudo-R2
.aic() -> f64
.bic() -> f64
.converged() -> bool
.fit_result() -> &AftFitResult          // n_observations, n_events, n_censored, n_features, iterations
.inference() -> Option<&AftInference>
.result() -> &AftResult
.predict_linear(&Mat<f64>) -> Col<f64>
.predict_quantile(&Mat<f64>, p: f64) -> Col<f64>   // p=0.5 is median; 0 at p=0, +Inf at p=1, NaN for p outside [0,1]
.predict_median(&Mat<f64>) -> Col<f64>             // predict_quantile(x, 0.5)
.predict_survival(&Mat<f64>, t: f64) -> Col<f64>   // P(T > t | x)
.predict_cdf(&Mat<f64>, t: f64) -> Col<f64>        // 1 - predict_survival
```

### `AftFitResult` / `AftInference` (`[VERIFIED: model.rs:60-130]`)
```rust
pub struct AftFitResult {
    pub coefficients: Vec<f64>, pub intercept: Option<f64>, pub scale: f64,
    pub log_likelihood: f64, pub null_log_likelihood: f64, pub aic: f64, pub bic: f64,
    pub n_observations: usize, pub n_events: usize, pub n_censored: usize,
    pub n_features: usize, pub iterations: u32, pub converged: bool,
}
pub struct AftInference {
    pub std_errors: Vec<f64>, pub z_values: Vec<f64>, pub p_values: Vec<f64>,
    pub ci_lower: Vec<f64>, pub ci_upper: Vec<f64>, pub confidence_level: f64,
    pub intercept_std_error: Option<f64>,
    pub log_scale_std_error: Option<f64>,   // None when scale is fixed (Exponential)
    pub vcov: Option<Mat<f64>>, pub information: Option<Mat<f64>>,
}
```
Same 7-field-vs-5-field summary gap as penalized GLM: AFT's per-coefficient
inference has `ci_lower`/`ci_upper` the shared `summary_output_dtype` lacks. Same
recommendation: a dedicated `aft_summary_output_dtype`. Additionally
`log_scale_std_error`/`intercept_std_error` are scalars, not per-term — these belong
as separate top-level fields on the **fit** output dtype (alongside `scale`), not in
the per-term summary list.

### `fit_aft` (column-major; not used — see Entry-Point Decision)
`fit_aft(time: &[f64], x: &[Vec<f64>], event: &[f64], options: &AftOptions) -> GlmEngineResult<AftResult>`
— `event` here is `&[f64]` (0.0/1.0), not `&[bool]` as the builder takes; confirms the
builder is the friendlier Python-facing shape (`event` as a Polars Boolean column is
more natural than caller-managed 0.0/1.0 floats).

## Priors / Offset / Vcov Wiring at the Expression Layer (Research Question 3)

**Mechanism confirmed by reading the actual `register_plugin_function` docstring
this session** (`.venv/bin/python -c "import polars.plugins, inspect;
print(inspect.getsource(...))"`): the function takes `args` (must be expressions —
per-row data) **and** a separate `kwargs: dict[str, Any] | None` — "Non-expression
arguments to the plugin function. These must be JSON serializable." This is exactly
the existing `PredictKwargs{prefix: String}` mechanism
(`#[polars_expr(output_type_func_with_kwargs=predict_output_dtype_with_prefix)] fn pl_xxx(inputs: &[Series], kwargs: PredictKwargs)`),
used today **only** for the `prefix` string on every `*_predict` expression
`[VERIFIED: src/expressions/regression.rs:3739-3744, 4000-4003 — read this session]`.

**Recommended wiring:**
- **Priors + vcov_type → `kwargs=`.** Define
  `#[derive(Deserialize)] struct PenalizedGlmKwargs { priors: Vec<PriorKwarg>, vcov_type: String }`
  where `PriorKwarg = (String, f64, f64)` or a small struct `{kind: String, loc: f64, scale: f64}`
  (serde supports both; a struct is more self-documenting on the JSON side: `{"kind":
  "normal", "loc": 0.5, "scale": 0.5}`). Python side: `priors: list[dict] | None = None`
  → `kwargs={"priors": priors or [], "vcov_type": vcov_type}`. This satisfies CONTEXT's
  "plain Python data (list of tuples or dicts)... no new Python classes" instruction
  exactly, and uses a mechanism that already exists and is already tested in this
  codebase (not a new invention). The dtype function must also take the kwargs
  parameter even though the output shape does not depend on it (pyo3-polars pairs
  `output_type_func_with_kwargs` with a `kwargs`-taking fit function at the macro
  level — confirmed by the macro invocation always appearing together in this
  codebase, never independently).
- **Offset → a zero-default expression input column, not `Option`.** No existing
  precedent for an optional per-row column in this codebase (searched; zero hits for
  "offset" anywhere in `src/`/`python/`). Recommend: Python kwarg
  `offset: pl.Expr | str | None = None`; when `None`, pass `pl.lit(0.0, dtype=pl.Float64)`
  (Polars broadcasts a scalar literal against the other same-length expression
  columns automatically in both `group_by` and `.over()` contexts — the same
  broadcast behaviour every scalar `pl.lit(...)` kwarg in this codebase already
  relies on). Rust side always calls `.offset(offset_col)` on the builder — a
  constant-zero offset is mathematically identical to no offset for every link
  function the engine supports (`link_inverse(eta + 0) == link_inverse(eta)`), so
  this needs no special-casing and avoids ever representing "no offset" as a
  sentinel/null column.
- **`family`/`distribution` → a plain string kwarg is NOT sufficient alone** for
  Poisson/Binomial (which need an additional `link=` sub-choice) and Tweedie (needs
  `power=`) and Logistic (needs `threshold=`) and NegBin (needs `theta=`). Recommend
  the Python builder take `family: str` plus the per-family extras as separate
  optional kwargs (`link: str | None`, `power: float | None`, `threshold: float`,
  `theta: float | None`), validated/dispatched into the right `PenalizedGlmFamily`
  variant on the Rust side — mirrors how `parse_hc_type`/`parse_solver_type` already
  dispatch a string kwarg into a Rust enum in this file.

### Pattern: Shared internal helper to avoid duplicating builder-construction logic
**What:** Both the PyModel `fit()` method and the expression `*_fit` function need to
build an identical `PenalizedGlmRegressorBuilder`/`AftRegressorBuilder` from the same
parsed family/priors/vcov/offset values. Recommend one private helper function per
engine in `regression.rs` (or a new `src/expressions/glm_common.rs` — this codebase
has no existing precedent for a shared cross-pymodel/cross-expression helper, since
every existing GLM's PyModel and expression construct their builder independently
with near-identical but copy-pasted code — e.g. `negative_binomial_fit` and
`PyNegativeBinomial::fit` both call `NegativeBinomialRegressor::builder()
.with_intercept(..).estimate_theta(..)...` separately). Given the much larger
parameter surface here (family+link+priors+vcov+offset vs. negative binomial's
theta+lambda+with_intercept), a shared helper is a reasonable deviation to reduce
duplication risk — but is **not required** by "pattern consistency" (the existing
pattern is actually duplication). Flag as a planner judgment call, not a hard
requirement.

### Pattern: Family dispatch from a Python string
**What:** Parse `family: &str` (+ optional `link`/`power`/`theta`/`threshold`) into
`PenalizedGlmFamily`. **Example**, following the existing `parse_hc_type`/
`parse_solver_type` string-to-enum dispatch style (`[VERIFIED: regression.rs:36-53]`):
```rust
fn parse_penalized_glm_family(
    family: &str, link: Option<&str>, power: Option<f64>,
    theta: Option<f64>, threshold: f64,
) -> PolarsResult<PenalizedGlmFamily> {
    Ok(match family {
        "poisson" => PenalizedGlmFamily::Poisson(match link {
            Some("identity") => PoissonLink::Identity,
            Some("sqrt") => PoissonLink::Sqrt,
            _ => PoissonLink::Log,
        }),
        "binomial" => PenalizedGlmFamily::Binomial(match link {
            Some("probit") => BinomialLink::Probit,
            Some("cloglog") => BinomialLink::Cloglog,
            _ => BinomialLink::Logit,
        }),
        "logistic" => PenalizedGlmFamily::Logistic { threshold },
        "negative_binomial" => PenalizedGlmFamily::NegativeBinomial { theta },
        "gamma" => PenalizedGlmFamily::Gamma,
        "tweedie" => PenalizedGlmFamily::Tweedie { power: power.unwrap_or(1.5) },
        other => return Err(polars_err!(ComputeError: "unknown penalized GLM family: {other}")),
    })
}
```

### Anti-Patterns to Avoid
- **Using the column-major `fit_poisson`/`fit_aft` functions anywhere in this
  codebase.** They exist for a different consumer (SQL/FFI front ends per the
  module doc); using them here would be an unprecedented, unnecessary second data
  path alongside the builder, with no benefit (see Entry-Point Decision).
- **Passing priors through `args=` as a serialized string column.** Possible
  (`pl.lit(json.dumps(priors))` → parse Rust-side), but `kwargs=` already exists for
  exactly this ("non-expression, JSON-serializable, constant across the call")
  purpose and is already wired into the macro (`output_type_func_with_kwargs`) — do
  not reinvent it as a string column.
- **Modifying the shared `summary_output_dtype`/`summary_output()` to add
  `ci_lower`/`ci_upper`.** This helper is used by ~10 other `*_summary_fit`
  functions across every existing GLM/linear model; adding fields there is a
  forbidden "reshape existing signature" (CONTEXT's additive-only principle,
  applied by extension) that would also force every other GLM's summary expression
  to backfill NaN CI columns it never asked for. Use a new, dedicated dtype.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Penalized GLM IRLS, priors, Laplace/sandwich/naive covariance | A custom IRLS loop or penalty term in `src/` | `anofox_regression::solvers::penalized_glm::{PenalizedGlmRegressor, PriorSpec, VcovType}` | The crate's engine is already R-validated (`glm`/`MASS::glm.nb`/`arm::bayesglm`-equivalent); this phase is pure FFI marshaling, exactly like every prior GLM phase |
| AFT censored-likelihood Newton-Raphson, quantile/survival/cdf functions | A custom survival-analysis implementation | `anofox_regression::solvers::aft::{AftRegressor, AftDistribution}` | Already validated against `survival::survreg`; hazard/survival/quantile math (including far-tail-stable log-survival for LogNormal) is already handled upstream |
| Priors/vcov as a per-row expression argument | A struct-typed Polars column / custom serialization scheme | The existing `kwargs=` JSON channel (`register_plugin_function(kwargs=...)`) | Already exists, already tested (`PredictKwargs`), explicitly documented by Polars itself as "non-expression arguments... must be JSON serializable" |
| "No offset" sentinel handling (`Option<Col<f64>>` across the FFI boundary) | A nullable-offset-column convention with per-row null checks | A `pl.lit(0.0)` default broadcast column | Adding zero to the linear predictor is a mathematical no-op for every link function here; avoids ever needing `Option` handling for a per-row input at the FFI boundary |

**Key insight:** Exactly as in Phase 16.1's research, every "new capability" here is a
thin marshaling problem — the engines are already implemented and R-validated
upstream. The two places genuine engineering judgment is needed are (1) collapsing
six/four Rust families into one Python class per engine (a design decision, not a
math problem), and (2) choosing `kwargs=` over `args=` for priors (an existing
mechanism this phase is the first to reuse for non-prefix purposes).

## Common Pitfalls

### Pitfall 1: Treating the Mann-Whitney/Wilcoxon schema-lock test from 16.1 as "don't touch"
**What goes wrong:** Phase 16.1 Plan 09 adds a test explicitly asserting the
expression schema is `["statistic", "p_value"]` and documents this as "unchanged in
16.1." An executor who sees a green, intentional-looking test might leave it alone
and let the full suite fail, or worse, revert their own 16.2 schema change to make
the old test pass again.
**Why it happens:** The test's existence and passing status look like a locked
invariant rather than a placeholder for "not yet implemented."
**How to avoid:** Grep `tests/*.py` for `expression_schema` and for the literal
string `["statistic", "p_value"]` before starting UPST-07; update that specific
assertion to the new 5-field list as part of this phase's tracer task, with a
comment citing "superseded by Phase 16.2 UPST-07."
**Warning signs:** `pytest tests/test_wilcoxon_mcnemar_parity.py -q` failing only
after this phase's expression change — that is the expected, correct failure this
pitfall describes; fix the test, not the feature.

### Pitfall 2: Reusing `summary_output_dtype` for penalized GLM / AFT and silently dropping CI
**What goes wrong:** Copy-pasting `negative_binomial_summary_fit` as the template
(the closest existing analog) reuses `summary_output_dtype`/`summary_output()`
verbatim, which has no `ci_lower`/`ci_upper` fields — `GlmInferenceResult`/
`AftInference` both compute them, so "full coverage" is silently violated.
**Why it happens:** The existing pattern is extremely copy-paste-friendly and every
other GLM's summary genuinely has no CI to report (their crate-level
`RegressionResult`/`GlmFitResult` types don't carry one).
**How to avoid:** Diff the fields on `GlmInferenceResult`/`AftInference` against
whatever summary dtype is chosen before considering the summary expression done;
either extend with a new dedicated dtype (recommended) or explicitly record CI
exposure as deferred in COVERAGE.md with a reason (not "forgot").

### Pitfall 3: Assuming `offset`/`event` need `Option<T>` plumbing at the FFI boundary
**What goes wrong:** Spending effort threading `Option<Col<f64>>` for offset or
treating a missing offset as a null-column special case, mirroring how optional
*scalar* kwargs (like NegBin's `theta: Option<f64>`) are handled elsewhere.
**Why it happens:** `theta: Option<f64>` **is** the established pattern for optional
scalars in this codebase (`inputs[1].f64()?.get(0)` naturally yields `Option<f64>`
from a nullable-literal column) — it's tempting to generalize that pattern to a
per-row column without noticing the mathematical shortcut available (zero-offset ==
no offset).
**How to avoid:** Default `offset` Python-side to a literal-zero broadcast column
(see Priors/Offset/Vcov Wiring section); the Rust side always has a real `Col<f64>`
and always calls `.offset(...)`, no `Option` branch needed.

### Pitfall 4: Forgetting `scripts/gen_stubs.py`'s `RUST_TO_PY` dict needs new entries
**What goes wrong:** New PyO3 method signatures introduce parameter/return type
strings not yet in `gen_stubs.py`'s `RUST_TO_PY` mapping (e.g. a `Vec<(String, f64,
f64)>` priors parameter, or `Option<Bound<'py, PyArray2<f64>>>` for a `vcov` getter if
the planner exposes the full covariance matrix) — `scripts/gen_stubs.py` is a regex
source-text mapper, **not** a live type introspector
`[VERIFIED: scripts/gen_stubs.py:1-30 — read this session]`. An unmapped type either
crashes generation or (worse) silently emits the raw Rust type string into the
`.pyi` file, which `tests/test_type_stubs.py`'s drift guard would then also fail on
only after a confusing stub diff.
**How to avoid:** After adding the new PyO3 classes, run
`.venv/bin/maturin develop && .venv/bin/python scripts/gen_stubs.py` and inspect the
diff for any raw-Rust-looking type string before committing; add missing entries to
`RUST_TO_PY` (e.g. `"Option<Bound<'py, PyArray2<f64>>>": "numpy.ndarray | None"` if
not already present — confirm by grep before assuming it's missing).
**Warning signs:** A `.pyi` diff containing `Vec<` or `Bound<'py,` verbatim.

### Pitfall 5: `PenalizedGlmFamily::Logistic{threshold}` and `.accuracy()`/`.separation()` only apply to two of six families
**What goes wrong:** Exposing `accuracy`/`separation` as unconditional getters that
return `None`/an empty `SeparationCheck` for non-binary families is correct
(`accuracy()` already returns `Option<f64>`, `separation()` always returns a
`&SeparationCheck` — empty-but-present for non-binary families per
`SeparationCheck::default()`), but a test or doc that asserts `accuracy` is always
populated after `.fit()` for every family would be wrong.
**How to avoid:** Mirror the upstream test's own structure (`binomial_links_match_glm`
asserts `accuracy` only on the Logistic-family fit, and
`!f.separation().has_separation` only in the binary-family test) when writing

## Code Examples

### Building the faer inputs for AFT (event as a real boolean column, not 0.0/1.0 floats)
```rust
// Source: anofox-regression-0.5.16 src/solvers/aft/regressor.rs:27-32 (builder signature),
// pattern follows build_xy_data's existing Series -> faer conversion style
// [VERIFIED: anofox-regression-0.5.16/src/solvers/aft/regressor.rs:27]
pub fn aft_fit(inputs: &[Series], kwargs: AftKwargs) -> PolarsResult<Series> {
    // inputs[0] = time, inputs[1] = event (bool), inputs[2] = distribution (str),
    // inputs[3] = with_intercept, inputs[4..] = x columns
    let time_series = inputs[0].f64()?;
    let event_bool = inputs[1].bool()?;
    let dist_str = inputs[2].str()?.get(0).unwrap_or("weibull");
    let with_intercept = inputs[3].bool()?.get(0).unwrap_or(true);

    let event: Vec<bool> = event_bool.into_no_null_iter().collect();
    let time_vec: Vec<f64> = time_series.into_no_null_iter().collect();
    let n = time_vec.len();
    let time = Col::from_fn(n, |i| time_vec[i]);

    let (x, _unused_y) = build_xy_data(inputs, 0, 4)?; // reuse existing helper; y_idx unused for AFT
    let dist = AftDistribution::from_name(dist_str)
        .ok_or_else(|| polars_err!(ComputeError: "unknown AFT distribution: {dist_str}"))?;

    let mut builder = AftRegressor::builder()
        .distribution(dist)
        .with_intercept(with_intercept);
    if !kwargs.priors.is_empty() {
        builder = builder.priors(kwargs.priors.iter().map(PriorKwarg::to_prior_spec).collect());
    }
    builder = builder.vcov_type(parse_vcov_type(&kwargs.vcov_type));

    match builder.build().fit(&x, &time, &event) {
        Ok(fitted) => aft_output(&fitted),
        Err(_) => aft_nan_output(),
    }
}
```
Note: `build_xy_data(inputs, 0, 4)` as written in this codebase assumes `inputs[0]`
is the `y` f64 column — for AFT, `inputs[0]` is `time` (also f64), so this helper is
directly reusable with no modification, just a different semantic label; its second
return value (parsed as `y: Col<f64>`) is simply unused/discarded here since `time`
was already extracted separately above for clarity. The executor should verify this
double-extraction is not wasteful/confusing and consider a small dedicated `build_x_only`
helper if `build_xy_data`'s signature proves awkward in practice.

### Offset default pattern (Python side)
```python
# Source: pattern derived from existing optional-scalar-kwarg handling
# (e.g. python/polars_statistics/exprs/regression.py's theta_lit pattern),
# generalized to a per-row default. No direct existing analog for offset.
def penalized_glm(
    y: Union[pl.Expr, str], *x: Union[pl.Expr, str],
    family: str = "poisson",
    offset: Union[pl.Expr, str, None] = None,
    ...,
) -> pl.Expr:
    if isinstance(y, str):
        y = pl.col(y)
    offset_expr = (
        pl.col(offset) if isinstance(offset, str)
        else offset if offset is not None
        else pl.lit(0.0, dtype=pl.Float64)
    )
    ...
    return register_plugin_function(
        plugin_path=LIB, function_name="pl_penalized_glm",
        args=[y.cast(pl.Float64), offset_expr.cast(pl.Float64), ..., *x_exprs],
        kwargs={"priors": priors or [], "vcov_type": vcov_type},
        returns_scalar=True,
    )
```

## Open Questions

1. **One class per engine, or one class per family (6 for GLM, 4 for AFT)?**
   - What we know: the Rust engine itself unifies all families behind one type;
     the roadmap's success-criteria wording uses singular "a PyModel."
   - What's unclear: whether the user, when reviewing the plan, will expect the
     existing six-separate-classes pattern to continue (since every other GLM in
     this codebase is a separate class) rather than a single parameterized one.
   - Recommendation: proceed with one class per engine (`PenalizedGLM`, `AFT`) as
     this research recommends, but flag this explicitly as a confirmable decision
     at `/gsd-discuss-phase` or in the plan's first checkpoint, since it is the
     single highest-leverage structural choice in the phase.

2. **AFT predict surface: one `kind=`-dispatched expression, or four separate ones?**
   - What we know: this codebase has zero precedent for a `kind=`-dispatch predict
     expression; every existing predict expression does exactly one thing.
   - What's unclear: whether four nearly-identical expressions (differing only in
     which `FittedAft` method they call and whether they take `p` or `t`) is
     tolerable duplication or worth collapsing.
   - Recommendation: four separate expressions (`aft_predict_quantile`,
     `aft_predict_median`, `aft_predict_survival`, `aft_predict_cdf`), consistent
     with the codebase's existing one-expression-per-capability granularity.

3. **Where does the full `vcov`/`information` matrix (when requested) surface, if at
   all, beyond the summary's per-term `std_error`/`ci_lower`/`ci_upper`?**
   - What we know: `FittedPenalizedGlm::vcov()`/`FittedAft`'s `AftInference.vcov`
     return `Option<&Mat<f64>>`; `IntoNumpy` already supports `&Mat<f64> ->
     PyArray2<f64>` (confirmed in `array_conversion.rs`), so a PyModel getter
     `vcov() -> Option<ndarray>` is straightforward.
   - What's unclear: whether "full coverage" requires this at the **expression**
     layer too (a `List[List[Float64]]` struct field is awkward in Polars) or
     PyModel-only is sufficient (mirroring how GLMM's full covariance, if ever
     exposed, would likely also be PyModel-only).
   - Recommendation: PyModel-only for `vcov`/`information`/`matrix_parameters`;
     document the expression-layer omission in COVERAGE.md with this rationale
     (matches the existing precedent of `FittedNegativeBinomial`'s richer accessors
     not all having expression-layer equivalents either).
