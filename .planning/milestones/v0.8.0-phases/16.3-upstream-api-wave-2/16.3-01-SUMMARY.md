## Accomplishments

- `ps.p_adjust(p, method=...)` reproduces R's `p.adjust` for all 7 methods (holm, hochberg, hommel, bonferroni, BH/fdr, BY, none) across 56 upstream reference cases, including NA/NaN preservation, `.over()`/`group_by` semantics, and build-time validation.

## Decisions Made

- Post-hoc tests are long-format `(values, groups)` expressions, not the existing N-separate-columns ANOVA convention, to preserve real group labels in `group1`/`group2` (CONTEXT.md decision, confirmed by RESEARCH.md's architectural analysis).
- `p_adjust`/`ptukey`/`qtukey` use a bare `Float64` output dtype (no `Struct` wrapper) -- the first use of this dtype shape in the codebase; every other `*_fit` function returns a `Struct`.
- Output field names `ci_lower`/`ci_upper` (not upstream's `conf_low`/`conf_high`) and `n1`/`n2` (not a `group_sizes` list) follow the project's existing naming conventions (`fisher_exact`, `bootstrap_ci`, 16.2's summary output).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 1 - Test tolerance too strict] `ptukey(qtukey(p))` round-trip relaxed from 1e-8 to 1e-6**
- **Found during:** Task 2 GREEN verification
- **Issue:** The plan's drafted `<behavior>` tolerance (1e-8) was tighter than `qtukey`'s own Newton-Raphson solver convergence criterion (`EPS = 1e-4` in `anofox-statistics-rs/src/posthoc/tukey_dist.rs`); composing `ptukey(qtukey(p))` inherits that solver's convergence slack. Observed max discrepancy across 210 `nranges==1` rows was ~8.6e-8, exceeding 1e-8 at one row (p=0.01, nmeans=3, df=2).
- **Fix:** Relaxed the round-trip assertion to 1e-6 (matching the same task's own lower-vs-upper-tail round-trip tolerance) and skipped the handful of reference rows where R's own `qtukey` returned NaN (non-convergent nmeans/df/p combinations) -- the round trip is undefined there, not a regression.
- **Files modified:** `tests/test_posthoc.py`
- **Verification:** All 6 Task 2 tests pass; `ptukey`/`qtukey` themselves still matched R at the plan's original 1e-10/1e-8 tolerances on every row.
- **Committed in:** `5bc104d` (Task 2 feat commit)

**2. [Rule 1 - Bug] NaN-unsafe `==` comparison in two pairwise tests**
- **Found during:** Task 3 GREEN verification
- **Issue:** `test_pairwise_na_rows_dropped` and `test_pairwise_group_by` compared lists of row-dicts with Python's `==`, which is always `False` for `nan != nan` (`ci_lower`/`ci_upper` are NaN for `pairwise_t_test`/`dunn_test`/some `tukey_hsd` edge cases). The underlying computed values were already identical; only the test's equality check was wrong.
- **Fix:** Added a NaN-aware `_rows_equal` helper and used it at both call sites.
- **Files modified:** `tests/test_posthoc.py`
- **Verification:** Both tests pass; full `tests/test_posthoc.py` suite green (209/209).
- **Committed in:** `a4356b8` (Task 3 feat commit)
