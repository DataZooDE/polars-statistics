## Summary

anofox-statistics 0.4.7 adds exactly one new module, `posthoc` (plus the standalone
`test_result` module), both re-exported at the crate root with zero name collisions against
this codebase. anofox-regression 0.5.17–0.5.21 add: `solvers::aid::heuristic` and
`solvers::eb_shrink` (0.5.17); GLMM family/offset/multi-factor-slopes builder methods (0.5.18,
additive to the existing `GlmmRegressorBuilder`); no new public API in 0.5.19 (LARS collinear
aliasing is a behaviour fix); `ModelInfo`/`HasModelInfo`, `diagnostics::augment`/`augment_with`,
and intercept-inference fill-in on the five non-penalized GLM families (0.5.20); and
`alias_tolerance` on OLS/WLS plus LARS fit-stat fill-in (0.5.21). Every signature below was
read directly from the crate source checked out at `~/projects/rust/anofox-statistics-rs` and
`~/projects/rust/anofox-regression` this session (both already pulled to their current `main`,
confirmed `git pull --ff-only` → "Bereits aktuell" / already up to date).

**The single most consequential finding this session:** the "intercept inference on every GLM"
success criterion (#2) does **not** require any new builder wiring. `PoissonRegressor`,
`NegativeBinomialRegressor`, `TweedieRegressor`, `GammaRegressor` and the three Binomial-link
PyModels (`Logistic`/`Probit`/`Cloglog`) already default `compute_inference = true`
`[VERIFIED: anofox-regression/src/core/options.rs:44]`, and every one of their
`fit()` calls in this codebase already runs through the shared `RegressionResult` struct whose
`intercept_std_error`/`intercept_t_statistic`/`intercept_p_value`/`intercept_conf_interval`/
`conf_interval_lower`/`conf_interval_upper` fields already exist on that struct
`[VERIFIED: anofox-regression/src/core/result.rs:78-106]` — they were simply left `None` by
the pre-0.5.20 GLM solvers. The 0.5.20 fix populates them; **zero of these fields are
currently exposed by any getter on any of the 7 GLM-family PyModel classes** `[VERIFIED:
grep -n "intercept_std_error\|intercept_t_statistic\|intercept_p_value\|intercept_conf_interval\|conf_interval_lower\|conf_interval_upper\|fn t_statistics" src/pymodels/py_{poisson,logistic,probit,cloglog,negative_binomial,tweedie,gamma}.rs — zero hits, this session]`.
This means "expose the new intercept inference" is purely **new additive getters**, mirrored
verbatim across 7 files from the exact `fitted.result().<field>` pattern already used for
`std_errors`/`p_values` in every one of those files. No behaviour, builder, or expression
change is needed to make the values exist — only to surface them.

**Second finding:** `diagnostics::augment`/`augment_with` substantially **overlaps**
mathematically with diagnostics this codebase already exposes piecewise
(`standardized_residuals_fit`, `studentized_residuals_fit`, `dffits_fit`,
`cooks_distance_fit`, `leverage_fit` in `src/expressions/regression.rs:1477-1830`, all backed
by the same `anofox_regression::diagnostics` functions `augment` itself calls internally —
confirmed by reading `augment_with`'s module doc, which states leverage comes "from the thin
QR of the (weighted) design", i.e. `compute_leverage`, already imported and used in this
codebase). `augment`'s value-add is **ergonomic bundling** (one call returns all seven
per-observation series plus the fitted mean, vs. five separate calls today) across a wider
model set (now includes all 6 GLM families, not just OLS/WLS as the piecewise diagnostics
currently cover for some fields). Recommend exposing it as new, additive surface (both a
PyModel convenience method and a new expression) rather than treating it as a hand-roll
replacement of the existing per-diagnostic functions — see Architecture Patterns and Common
Pitfalls.

**Third finding:** the post-hoc tests (`tukey_hsd`, `pairwise_t_test`, `dunn_test`) take a
**long-format** signature — `(values: &[f64], groups: &[G])`, one flat values column plus one
group-label column, `G: Ord + Clone` — which is the opposite shape from this codebase's
existing multi-group convention (`one_way_anova`/`kruskal_wallis` take **N separate same-length
columns**, one per group, no label column at all). Long format is the only shape that matches
both the Rust signature and R's own argument convention
(`pairwise.t.test(values, groups, ...)`), and it is required to preserve real group labels in
the `group1`/`group2` output fields — a wide re-mapping would force synthetic
`"group_0"`/`"group_1"` labels and lose this. This is a **genuinely new expression-input
convention** for this codebase; recommend `G = String` only (cast the group column to `Utf8`
Python-side) to avoid generic dispatch in Rust.

**Primary recommendation:** Treat this phase as six independently-committable Wave-1 slices
(posthoc + p_adjust + ptukey/qtukey; GLM intercept-inference getters; `augment`; GLMM families/
offset/per-factor slopes; OLS/WLS `alias_tolerance` + LARS fit-stat getters; `eb_shrink` +
`ModelInfo` + the AID-heuristic decision), each touching a distinct set of files with almost
no shared-file collisions (see Architecture Patterns — "Avoiding Wave-1 File Collisions"),
followed by a Wave-2 docs/stubs/skills/CHANGELOG pass. No new PyO3 classes need registering in
`src/lib.rs` / `src/pymodels/mod.rs` / `python/polars_statistics/__init__.py`'s Rust-binding
import block for any item in this phase if post-hoc tests and `eb_shrink` are kept
expression-only (matching the established precedent set by 16.1's Jarque-Bera/Cohen's
d/bootstrap_ci, none of which got a dedicated PyModel class) — this sidesteps the only
genuinely contentious shared-file hazard.

### `p_adjust`
```rust
pub fn p_adjust(p: &[f64], method: PAdjustMethod) -> Vec<f64>
```
`PAdjustMethod` ∈ `{Holm, Hochberg, Hommel, Bonferroni, BH, BY, None}`, `FromStr` parses R's
names case-insensitively (`"holm"`, `"hochberg"`, `"hommel"`, `"bonferroni"`, `"bh"`/`"fdr"`,
`"by"`, `"none"`). NaN values are kept as NaN and excluded from the comparison count `n`
(R's `NA` semantics) — this needs an explicit NaN-preservation pytest, since it is an easy
corner to silently drop. **Elementwise, same length as input** — not a reduction.

### `ptukey` / `qtukey`
```rust
pub fn ptukey(q: f64, nmeans: f64, df: f64, nranges: f64, lower_tail: bool) -> f64
pub fn qtukey(p: f64, nmeans: f64, df: f64, nranges: f64, lower_tail: bool) -> f64
```
Ports of R's `ptukey.c`/`qtukey.c`; agree with R to < 1e-10 (`ptukey`) / < 1e-8 (`qtukey`).
NaN for NaN args or invalid parameters (`df < 2`, `nranges < 1`, `nmeans < 2`).
**Scalar-per-row, same length as input** (each argument is a column; this is a vectorized
distribution function, not a reduction) — same shape class as `p_adjust`.

### New dtype pattern: bare `Float64`, elementwise (`p_adjust`, `ptukey`, `qtukey`)
**What:** every existing `output_type_func` in this codebase returns a `Struct` (confirmed by
reading all 15 functions in `output_types.rs` plus every dtype fn in `regression.rs`/
`categorical.rs`/`nonparametric.rs` this session — none return a bare scalar dtype). `p_adjust`/
`ptukey`/`qtukey` are genuinely new in that they transform a column into a same-length column
of a single value, with no second field to justify a Struct. The existing `*_predict`
expressions already use the matching **shape** (`returns_scalar=False`, same-length output)
but wrap it in a prefixed Struct for their multi-field outputs (`output_type_func_with_kwargs`
+ `PredictKwargs{prefix}}`). For a single-field elementwise output, the simplest, most direct
new dtype function is a bare `Field::new(name, DataType::Float64)` (no `Struct` wrapper) paired
with `returns_scalar=False` Python-side — mechanically simple, no existing exact precedent to
copy line-for-line, but every piece of the mechanism (`output_type_func=`, `returns_scalar=False`)
is independently proven elsewhere in this codebase.
**Example:**
```rust

// only one field, so skip the Struct/kwargs machinery entirely.
fn float64_elementwise_output_dtype(_input_fields: &[Field]) -> PolarsResult<Field> {

}

}
```

### New wiring pattern: long-format post-hoc tests (`G = String`)
**What:** `pairwise_t_test`/`tukey_hsd`/`dunn_test` take `(values: &[f64], groups: &[G])`,
`G: Ord + Clone`. Recommend fixing `G = String` in the FFI layer (cast the Python group column
to `Utf8` before calling, via `inputs[1].str()?.into_no_null_iter().map(String::from).collect()`)
rather than attempting a generic dispatch over the group column's Polars dtype — the `Ord`
requirement on `G` (needed for `BTreeMap`-based grouping in `group_index`) is trivially
satisfied by `String`, and every downstream `group1`/`group2` output field is naturally a

columns will show up as their string representation in `group1`/`group2`) rather than an
oversight.

## Common Pitfalls

### Pitfall 1: Assuming "intercept inference on every GLM" needs a builder/fit change
**What goes wrong:** Spending a task adding `.compute_inference(true)` calls or confidence-level
threading to the 5 GLM-family `fit()` methods, when every one of them already defaults
`compute_inference = true` and already populates the (currently unexposed) fields.
**Why it happens:** The roadmap phrasing ("intercept inference on every GLM... is exposed")
reads like new computation is needed.
**How to avoid:** This session confirmed by reading `RegressionOptions`'s `Default` impl
(`compute_inference: true`) and each of the 7 GLM PyModel `fit()` bodies that inference is
already requested; the only missing piece is the getter. Verify with
`grep -n "compute_inference" src/pymodels/py_<model>.rs` before adding any builder call — if
the model already calls `.compute_inference(slf.compute_inference)` (Poisson/Logistic) or
never calls it but defaults to `true` (Probit/Cloglog/NegativeBinomial/Tweedie/Gamma — these
never call `.compute_inference()` at all, confirmed; they rely on the builder default), no
`fit()` change is needed either way.

### Pitfall 2: Reusing `summary_output_dtype` for post-hoc comparisons or `augment`
**What goes wrong:** Copy-pasting the existing 5-field `summary_output`/`summary_output_dtype`
(`term`/`estimate`/`std_error`/`statistic`/`p_value`) as the template for post-hoc comparisons
or `augment`'s 7 per-observation series, silently dropping fields that don't fit (`group1`/
`group2`/`p_adj`/`conf_low`/`conf_high` for post-hoc; `resid_type`/all seven series for
`augment`) or affecting the ~10 other callers of the shared dtype.
**Why it happens:** `summary_output_dtype` is this codebase's most copy-paste-friendly
existing pattern.
**How to avoid:** Both post-hoc comparisons and `augment` need **dedicated** new dtype
functions (per the New dtype / Architecture Patterns sections above) — this mirrors 16.2's own
explicit decision not to extend the shared `summary_output_dtype` for penalized GLM/AFT's CI
fields, for the same reason (blast radius across unrelated callers).

### Pitfall 3: Treating `eb_shrink` / post-hoc tests as per-Polars-group reductions
**What goes wrong:** Writing `ps.eb_shrink(...)` or `ps.tukey_hsd(...)` expecting them to be
used inside `.group_by(outer_col).agg(...)` the way `ps.t_test(...)` is — but both functions
need **all** rows of their input at once (all groups' estimates for `eb_shrink`; all group
labels for the post-hoc tests), so wrapping them in an *additional* outer `group_by` changes
their semantics (each outer group would get its own independent `tukey_hsd`/`eb_shrink` call
over only its own rows, which may or may not be the intended unit of analysis).
**How to avoid:** Document explicitly, mirroring the existing `one_way_anova` docstring's
warning ("Use on the full DataFrame... do not use inside group_by unless each group contains
all ANOVA groups") — the identical caveat applies here.
**Warning signs:** A test that calls `ps.eb_shrink(...)` inside `.group_by(...).agg(...)` and
asserts results differ per outer group without that being the deliberate intent.

### Pitfall 4: Assuming `Probit`/`Cloglog` implement `Augmentable`
**What goes wrong:** Adding an `.augment()` method to `PyProbit`/`PyCloglog` by analogy with
`PyLogistic`, when upstream's `impl Augmentable for` list (8 entries, confirmed by grep this
session) names `FittedLogistic` but not `FittedProbit`/`FittedCloglog`.
**How to avoid:** Re-run `grep -rn "impl Augmentable for" ~/projects/rust/anofox-regression/src/`
at implementation time (upstream could add these before 16.3 executes) before adding the
method to any class beyond the 8 confirmed types; if still absent, add `.augment()` only to
`OLS`/`WLS`/`Poisson`/`Logistic`/`NegativeBinomial`/`Tweedie`/`Gamma` and record Probit/Cloglog
as a documented gap (upstream limitation, not this codebase's choice).

### Pitfall 5: Forgetting the three-file expression-registration chain
**What goes wrong:** Adding a new Rust `#[polars_expr]` function and its Python builder in
`exprs/posthoc.py`, but forgetting to add the import to **both** `exprs/__init__.py` **and**
the top-level `python/polars_statistics/__init__.py` — the function compiles and the Rust
plugin registers it, but `ps.tukey_hsd(...)` raises `AttributeError` because it was never
re-exported at the package's top level.
**How to avoid:** Treat the three-file chain (new module → `exprs/__init__.py` → top-level
`__init__.py`) as one atomic edit set per new Python-facing function; grep
`grep -n "<function_name>" python/polars_statistics/__init__.py python/polars_statistics/exprs/__init__.py`
before considering a new expression "done".

## Open Questions

1. **`TestResult` — expose a Python counterpart, or opt out?**
   - What we know: the roadmap's own wording anticipates this may have "no Python counterpart";
     every existing Test PyModel class (`TTestInd`, `MannWhitneyU`, `Wilcoxon`, `BrunnerMunzel`,
     `ShapiroWilk`, `DAgostino`, `KruskalWallis`, `YuenTest`, `BrownForsythe`, `Bootstrap`)
     already has a generic `to_dict()`/`summary()` via `src/pymodels/ergonomics.rs`'s
     property-introspection mechanism, in each class's own native field names.
   - What's unclear: whether the user wants a *second*, standardized 13-field dict shape
     (`.to_test_result()`) alongside each class's existing native `to_dict()`, for
     cross-test-type tooling (e.g. building a results table across heterogeneous tests).
   - Recommendation: **opt out** (record in COVERAGE.md per the roadmap's own anticipated
     wording) — the existing `ergonomics.rs` mechanism already gives every test class a tidy
     dict in its native shape; a second, parallel "unified" shape for the same data is
     redundant complexity, not missing coverage. If the user disagrees at `/gsd-discuss-phase`,
     the low-cost alternative is a single additive `.to_test_result()` method per Test class
     using the already-written upstream `From<&T>` impls — zero new Rust logic, just a thin
     wrapper, so reversing this recommendation later costs little.

2. **AID heuristic (`compute_aid`/`compute_aid_anomalies`) — integrate, or opt out?**
   - What we know: this codebase already exposes the richer, IC-based `AidClassifier` as the
     `Aid` PyModel; the new heuristic is explicitly "lightweight"/"fit-free", moved from a
     DuckDB extension's zero-dependency code path; the crate's own doc says it "complements,
     and does not replace" the existing classifier; the roadmap's success criterion #3 lists
     the AID heuristic alongside `TestResult` as an *expected* opt-out candidate, not a
     mandatory inclusion.
   - What's unclear: whether the user's "full API coverage" instruction overrides that
     roadmap-level hint, given demand-classification is adjacent to (but not the same as) the
     v2-deferred `FCST-01` Forecast Integration scope.
   - Recommendation: **opt out**, record the reasoning above in COVERAGE.md — mirrors the
     roadmap's own expectation. If the user wants it anyway, it is a low-risk, mechanical
     addition to the existing `py_aid.rs` (same file, no new class).

3. **GLM/OLS/WLS slope-level CI at the expression layer — extend `summary_output_dtype`, or PyModel-only?**
   - What we know: the shared `summary_output_dtype` (5 fields, `term`/`estimate`/
     `std_error`/`statistic`/`p_value`) is used by ~10 existing `*_summary_fit` functions
     across OLS/WLS/Ridge/every GLM; none currently report CI at the expression layer. 16.2
     declined to extend this shared dtype for penalized GLM/AFT's *own* separate dtype, citing
     blast radius across unrelated callers.
   - What's unclear: whether "intercept inference on every GLM... is exposed" (roadmap success
     criterion #2) is satisfied by PyModel-only getters (this research's primary
     recommendation) or requires the expression-layer summary to also carry CI for every
     affected GLM's slope terms, which would mean touching all ~10 shared-dtype callers
     additively (new trailing `ci_lower`/`ci_upper` fields, NaN for callers whose
     `RegressionResult` doesn't populate them).
   - Recommendation: **PyModel-only** for this phase (lower blast radius, matches 16.2's own
     precedent for the identical class of decision); document the expression-layer CI gap in
     COVERAGE.md with this rationale. Revisit only if `/gsd-discuss-phase` surfaces an explicit
     user preference for expression-layer CI.

4. **`ModelInfo` — full 29-class rollout in this phase, or scoped to the classes already touched?**
   - What we know: the getter is a uniform 3-line body (`fitted.model_info()` → a 3-key dict)
     across all 29 implementing types; "full coverage" favors doing all of them.
   - What's unclear: whether a 29-file mechanical pass belongs in this phase's scope (new
     upstream capability) or is better split into its own small, low-risk plan to avoid
     bloating the Wave-1 slices that are otherwise scoped around a single capability each.
   - Recommendation: do the full rollout, but as its **own** Wave-1 plan/task (not folded into
     the GLM-intercept-inference or GLMM slices), since it touches a disjoint, much larger
     file set and has zero interaction with the other five slices' logic.

5. **`augment` expression surface: one combined expression, or per-model additions to the
   existing diagnostics family?**
   - See Assumption A4 — left open for the planner, either is additive and low-risk.
