# Phase 16.3: Code Review Report

**Reviewed:** 2026-10-15T20:00:33Z

## Summary

Reviewed the 16.3 "upstream API wave 2" diff: `p_adjust`/`ptukey`/`qtukey`/post-hoc
pairwise expressions (`posthoc.rs`), `eb_shrink` (`shrinkage.rs`), the combined
`ps.augment` expression and the per-class `.augment()` PyModel method
(`regression.rs`, `augment.rs`), `ModelInfo` getters across 30 `PyModel` classes
(`model_info.rs` + 30 `py_*.rs` files), GLMM family/offset/per-factor-slope
plumbing (`py_glmm.rs`), and `alias_tolerance` threading across OLS/WLS
fit/summary/predict/formula.

Most of this surface is careful and well-tested: the `ModelInfo` rollout
correctly anticipates the three PyModel classes that type-erase their fitted
model behind `Box<dyn FittedRegressor>` (`ElasticNet`, `RLS`, `BLS`) by
capturing `ModelInfo` at the concrete fit site before boxing (documented in
`COVERAGE.md` note 4 and covered by `test_model_info_boxed_refit_keeps_own_type`).
GLMM's `nb_theta` (true fixed-theta support) is implemented correctly and
R-validated (`test_negative_binomial_fixed_theta_matches_glmer`). `alias_tolerance`
is threaded consistently and exhaustively across every OLS/WLS entry point and
validated in both Rust and Python. `p_adjust`/`ptukey`/`qtukey` NaN/argument-
validation semantics match R exactly (verified against the upstream
`anofox-statistics` 0.4.7 source) and post-hoc group handling correctly rejects
single-group / empty input via the upstream `group_index` validation, degrading
to an empty list rather than panicking.

One correctness bug was found and confirmed by direct reproduction against the
compiled extension: `ps.augment(model="negative_binomial", theta=...)` silently
ignores the user-supplied fixed theta and always uses the ML-estimated theta
instead — in direct contradiction of its own documented contract. This is the
same class of bug the phase's own `tweedie`/`link_power` precedent fix
addressed, but it was not applied to the `negative_binomial` branch of
`augment_fit`. Two further documentation/quality issues are noted below.

## Critical Issues

### CR-01: `ps.augment(model="negative_binomial", theta=...)` silently ignores the fixed theta

**File:** `src/expressions/regression.rs:3118-3129`

**Issue:**

`AugmentKwargs::theta` is documented as "Fixed negative-binomial theta
(dispersion); `None` estimates it" (`src/expressions/regression.rs:2847-2848`),
and the Python wrapper repeats the same contract ("Fixed negative-binomial
dispersion ... `None` estimates it from the data",
`python/polars_statistics/exprs/regression.py:2163-2165`). The dispatch arm,
however, is:

```rust
"negative_binomial" => {
    let mut b = NegativeBinomialRegressor::builder()
        .with_intercept(with_intercept)
        .max_iterations(kwargs.max_iter)
        .tolerance(kwargs.tol);
    b = match kwargs.theta {
        Some(t) => b.theta(t),
        None => b.estimate_theta(true),
    };
    let m = b.build();
    run_augment!(m.fit(&x, &y))
}
```

`NegativeBinomialRegressorBuilder::estimate_theta` defaults to `true`
(`anofox-regression-0.5.22/src/solvers/negative_binomial.rs:1064-1071`), and
`.theta(t)` only sets the *starting value* for the theta MLE when
`estimate_theta` stays `true` (`negative_binomial.rs:1126-1128`, and the fit
loop at `negative_binomial.rs:205-207` unconditionally overwrites `theta` via
`estimate_theta_ml` on every outer iteration when `estimate_theta` is true).
Because this branch never calls `.estimate_theta(false)` when a fixed `theta`
is supplied, the builder keeps its default `estimate_theta = true`, and the
user's `theta` is overwritten by the ML estimate before the first outer
iteration completes — the fit is identical to the fully-estimated case,
regardless of what `theta` was passed.

Confirmed by direct reproduction against the compiled extension (`anofox-regression 0.5.22`):

```
truly-fixed theta=2.0 (estimate_theta=False) coefs: [-0.18282333 -0.29424021 -0.51037269]
theta=2.0, estimate_theta left at builder default True  coefs: [-0.18621105 -0.29922724 -0.51139552]
fully ML-estimated theta                                coefs: [-0.18621105 -0.29922724 -0.51139552]

ps.augment(..., model="negative_binomial", theta=2.0) fitted values
  == the fully-estimated-theta fit (not the truly-fixed-theta fit)
```

The existing test `test_negative_binomial_fixed_theta_matches_estimated` in
`tests/test_augment.py:382-405` does not catch this: it only asserts that the
"fixed" and "estimated" fits are *close* (because `fitted`/mean-response values
barely depend on theta at this tolerance), which is also exactly what you'd see
if `theta` were silently ignored — the test currently cannot distinguish
"theta correctly fixed" from "theta silently ignored."

The GLMM `nb_theta` path does this correctly for comparison
(`src/pymodels/py_glmm.rs` — the upstream builder's `nb_theta(t)` call is a
true fixed-theta API, R-validated by `test_negative_binomial_fixed_theta_matches_glmer`
in `tests/test_glmm.py:414-428`), which is why this is a regression specific to
`augment_fit`'s dispatch, not a crate limitation.

**Fix:**

```rust
"negative_binomial" => {
    let mut b = NegativeBinomialRegressor::builder()
        .with_intercept(with_intercept)
        .max_iterations(kwargs.max_iter)
        .tolerance(kwargs.tol);
    b = match kwargs.theta {
        Some(t) => b.theta(t).estimate_theta(false),
        None => b.estimate_theta(true),
    };
    let m = b.build();
    run_augment!(m.fit(&x, &y))
}
```

Also strengthen `test_negative_binomial_fixed_theta_matches_estimated` (or add
a new test) to assert the fits actually *differ* at a fixed theta far from the
ML estimate (e.g. compare `std_residual`/`cooks_d`, which depend on the
dispersion, not just `fitted`), so a future regression of this kind is caught.

## Warnings

### WR-01: `ps.augment()`'s `weights` docstring contradicts its own code for `model="wls"`

**File:** `python/polars_statistics/exprs/regression.py:2154-2156`, contradicted by `:2207-2208`

**Issue:** The expression-level `augment()` docstring states:

```
weights : pl.Expr or str, optional
    Prior weights. Required (and only valid) with model="wls"; when
    omitted for WLS the fit's own weights are used.
```

"Required" and "when omitted ... used" directly contradict each other, and the
actual code three lines below (and 50 lines later) raises `ValueError` when
`model="wls"` and `weights is None`:

```python
if model_l == "wls" and weights is None:
    raise ValueError("ps.augment: model='wls' requires weights")
```

`ps.augment()` fits a fresh model on every call — there is no "fit's own
weights" to fall back to (unlike `WLS.augment()`, the PyModel method, which
*does* reuse the already-fitted model's stored weights when `weights` is
omitted — see `src/pymodels/augment.rs:20-21` and
`tests/test_augment.py:539-547`). The sentence appears to be copied from the
PyModel method's docstring without adjusting for the expression's different
(fit-from-scratch) semantics, and will mislead a user into omitting `weights`
for `ps.augment(model="wls")` expecting it to "use the fit's own weights,"
only to get a `ValueError`.

**Fix:** Correct the expression docstring to match its actual, tested
behavior, e.g.:

```
weights : pl.Expr or str, optional
    Prior weights. Required with model="wls" (the expression fits fresh
    on every call, so there is no already-fitted model to borrow weights
    from); invalid with any other model.
```

### WR-02: A single non-finite value silently discards an entire post-hoc comparison, not just that row

**File:** `src/expressions/posthoc.rs:313-327` (`long_format`), consumed by `tukey_hsd_fit`/`pairwise_t_test_fit`/`dunn_test_fit`

**Issue:** `long_format` drops a row only when its value `is_none()` or
`is_nan()`:

```rust
if let (Some(v), Some(g)) = (v_ca.get(i), g_ca.get(i)) {
    if !v.is_nan() {
        out_values.push(v);
        out_groups.push(g.to_string());
    }
}
```

It does **not** drop rows where the value is `+Inf`/`-Inf` (finite-but-not-NaN
check is missing — it should be `v.is_finite()`, mirroring `augment_fit`'s own
validity scan a few hundred lines later in `regression.rs`, which does check
`v.is_finite()`). A single `Infinity` in the `values` column is passed through
to `anofox_statistics::{tukey_hsd, pairwise_t_test, dunn_test}`, whose
`ensure_finite` rejects it with an `Err`, which `posthoc.rs` then maps to
`pairwise_empty_output()` (empty list, no exception) — losing **every**
pairwise comparison for the whole call, not just the comparisons touching the
infinite row. This is "never an exception" working as designed, but the
silent full-result loss from one contaminated row is a sharp edge that is not
called out in `ps.tukey_hsd`/`ps.pairwise_t_test`/`ps.dunn_test`'s docstrings
(which only mention null/NaN row-dropping), and could hide a real data
problem inside a `group_by().agg()` pipeline that an analyst has no reason to
suspect (no error, just unexpectedly empty results for one group).

**Fix:** Either (a) filter `!v.is_finite()` in `long_format` (dropping just
the offending row, consistent with R's `TukeyHSD`/`pairwise.t.test`, which
would themselves error loudly on `Inf` rather than silently drop the whole
comparison set), or (b) if the empty-output-on-any-non-finite-value behavior
is intentional, document it explicitly in the three public docstrings
alongside the existing null/NaN note.

## Info

### IN-01: Augment's internal validity scan re-derives `.f64()` conversions already proven to succeed

**File:** `src/expressions/regression.rs:3033-3048`

**Issue:** `augment_fit` validates every `x` column via `col.f64()?` in an
earlier loop (`:3003-3011`), then rebuilds the design matrix with
`inputs[2 + col].f64().unwrap()...unwrap()` (`:3033-3039`) and the weights
column with `w_ca.get(...).unwrap()` (`:3043-3045`). These `.unwrap()` calls
are safe today only because the earlier loop already proved the conversions
succeed and the row is in `valid_indices` — but the safety argument is
implicit and spread across ~40 lines rather than being locally obvious at the
`unwrap()` call sites. A future refactor that reorders or short-circuits the
validity scan could silently turn these into reachable panics on user input
("process crash" risk, contrary to the file's own stated convention: "Shape
mismatch: `ToFaer` panics (debug) or silently truncates"). Prefer propagating
with `?`/`ok_or_else` (as `build_xy_data` does a few hundred lines above, via
`.f64().ok().and_then(...).unwrap_or(f64::NAN)`) or add a short comment at
each `unwrap()` site explaining the invariant it relies on, so the safety
property survives future edits.
