## Cross-Phase Integration

The integration checker (gsd-integration-checker) found **13/13 phase-boundary contracts wired** and **5/5 E2E flows complete**. There are no broken flows and no blocking gaps.

**Verified connections**

- 13 → 14 → 15: the `marketplace.json` → `plugin.json` → `skills/` chain resolves. Phase 14's production SKILL.md files replace the stubs from Phase 13. The harness (`scripts/verify_skill_examples.py`) passes with 0 FAIL.
- 15 → 16: `python/polars_statistics/_plugin/` is a byte-identical mirror of `plugins/polars-statistics/`. CI enforces this with `verify_wheel_bundling.py --drift-only` (ci.yml:37). (PKG-01)
- 16.1–16.3 → package: the new expression modules (aft, penalized_glm, posthoc, shrinkage, resampling) are re-exported in `src/expressions/mod.rs`. `PyAFT` and `PyPenalizedGLM` are registered in `src/lib.rs`. All builders are exported from `python/polars_statistics/__init__.py` and `exprs/__init__.py`, the `.pyi` stubs contain them, and the stub drift guard runs in CI. (UPST-03/05/06/08/09)
- 16.1–16.3 → skills: the regression, anova and results skills document penalized GLM, AFT, tukey_hsd, pairwise_t_test, dunn_test, p_adjust, augment and eb_shrink. (UPST-04/07/10)
- 16.4 → CI: `ruff check .` runs in the lint job (ci.yml:31). (QUAL-01)
- 17: all 18 version sources are at 0.8.0, and `check_version_alignment.py` passes, also via `tests/test_version_alignment.py`. The release smoke test on 3.9 and 3.12 passed, and 0.8.0 is on PyPI through OIDC. (REL-07/08)

**E2E flows (5/5):** pip install, then import of the new API; calling a new expression through a Rust plugin; reading a skill and running its examples; a skill edit in a PR caught by the drift guard; and the version-aligned release.

**Warning (non-blocking, VERIFY-01):** `scripts/verify_skill_examples.py` is not invoked in `.github/workflows/ci.yml`, which I confirmed by grep. It runs only in the local and release gates, so skill examples could drift from the API between releases without CI catching it. Recommendation: add the harness as a CI step after the extension build.
