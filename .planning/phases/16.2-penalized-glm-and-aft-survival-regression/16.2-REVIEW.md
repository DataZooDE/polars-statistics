# Phase 16.2: Code Review Report

**Reviewed:** 2026-10-09

## Summary

Reviewed the new penalized-GLM / AFT survival expression and PyO3 surface (`src/expressions/{penalized_glm,aft}.rs`, `src/pymodels/py_{penalized_glm,aft}.rs`), the Python builder layer (`python/polars_statistics/exprs/regression.py`), the additive Mann-Whitney/Wilcoxon fields, stub/export wiring, docs, and the test suite, cross-checked against the vendored `anofox-regression` 0.5.22 source where upstream semantics mattered (dispersion/vcov scaling, AFT inference curvature).

Most of the new surface is careful and correct: the GLM `vcov` dispersion-scaling fix (`penalized_glm_covariance_scale`) was verified line-by-line against upstream's `DispersionRule::covariance_scale` and is exactly right; the AFT `log_scale` Wald computation was verified against upstream's own intercept inference and matches to machine precision (also unit-tested in `aft.rs`); offset/null-policy interactions are handled with real care and matching doc comments. However, one genuine correctness bug was found and confirmed by direct reproduction: the four `aft_predict_*` Polars expressions silently misinterpret invalid event codes (e.g. R's `1`/`2` coding) as right-censored instead of rejecting them, in direct contradiction to the documented and tested contract that `aft`/`aft_summary` enforce. A secondary documentation/process gap (missing `aft_formula_predict_*` with no corresponding COVERAGE.md OPT-OUT row) and two minor quality nits round out the findings.

## Critical Issues

### CR-01: `aft_predict_quantile`/`_median`/`_survival`/`_cdf` silently misinterpret invalid event codes instead of rejecting them

**File:** `src/expressions/aft.rs:560-582` (function `aft_predict_impl`)
**Issue:**

`aft_fit`/`aft_summary_fit` build `(x, time, event)` via `aft_inputs()` (`src/expressions/aft.rs:142-216`), which strictly validates that a non-Boolean `event` column contains **only** `0.0`/`1.0`, returning an `Err` (→ all-NaN struct) for anything else — e.g. R's `1`/`2` coding. This is documented ("any other value ... fails the whole fit rather than being silently misread", `docs/api/regression/survival.md:40-42`) and unit-tested (`tests/test_aft.py::TestAftEventCoding::test_event_coding_invalid_gives_nan_struct`).

The four predict expressions do **not** reuse `aft_inputs()`. Instead, `aft_predict_impl` builds its own `event_bool` conversion:

```rust
_ => {
    let casted = event_series.cast(&DataType::Float64)?;
    let ca = casted.f64()?;
    (0..n_rows).map(|i| ca.get(i).map(|v| v == 1.0)).collect()
}
```

Any non-null numeric value that is not exactly `1.0` (`2.0`, `-1.0`, `0.5`, ...) silently becomes `Some(false)` — i.e. "censored" — with no error and no NaN. This directly contradicts the documented and tested invariant and produces silently wrong fitted models and predictions for any caller whose `event` column uses a different numeric convention (R's classic `1`/`2` survival coding is explicitly called out elsewhere in this same codebase as the motivating example).

Confirmed by direct reproduction (same data, row 0's `event` corrupted from `1.0` to `2.0`):

```
aft() with invalid event code -> NaN struct (correct):            intercept = nan
aft_predict_median() with the same invalid event code:            [2.4517, 4.2056, 4.1216]  (wrong, no error)
aft_predict_median() with the original, valid event column:       [2.3176, 4.2522, 4.1569]
```

No existing test (`tests/test_aft.py`, `tests/rust_api.rs`) exercises an invalid event code through the predict path — the gap is real, not merely untested-but-handled.

**Fix:** Reuse the same `event` validation `aft_inputs()`/`aft_fit` use (reject anything other than Boolean or exact `0.0`/`1.0`, return the NaN-prediction struct on violation) inside `aft_predict_impl`, e.g.:

```rust
let event_vals: Vec<Option<bool>> = match event_series.dtype() {
    DataType::Boolean => {
        let ca = event_series.bool()?;
        (0..n_rows).map(|i| ca.get(i)).collect()
    }
    _ => {
        let casted = event_series.cast(&DataType::Float64)?;
        let ca = casted.f64()?;
        let mut out = Vec::with_capacity(n_rows);
        for i in 0..n_rows {
            match ca.get(i) {
                None => out.push(None),
                Some(v) if v == 0.0 => out.push(Some(false)),
                Some(v) if v == 1.0 => out.push(Some(true)),
                Some(_) => return prediction_nan_output_with_prefix(n_rows, prefix),
            }
        }
        out
    }
};
```
and use `event_vals` in place of the current permissive `event_bool`/`event_null_mask` construction.

## Warnings

### WR-01: `aft_formula_predict_*` is missing entirely, with no COVERAGE.md OPT-OUT entry recording the decision

**File:** `python/polars_statistics/exprs/regression.py` (no `aft_formula_predict*` function exists); `.planning/phases/16.2-penalized-glm-and-aft-survival-regression/COVERAGE.md:62-65`
**Issue:** `penalized_glm` has a full formula quartet (`penalized_glm_formula`, `_formula_summary`, `_formula_predict`), matching CONTEXT's "Pattern consistency ... the formula interface if the existing GLMs support it." AFT only has `aft_formula`/`aft_formula_summary` — none of `aft_formula_predict_quantile`/`_median`/`_survival`/`_cdf` exist (confirmed: `grep -n "^def aft" python/polars_statistics/exprs/regression.py` lists only `aft`, `aft_summary`, the four `aft_predict_*`, `aft_formula`, `aft_formula_summary`).

COVERAGE.md's "aft: formula interface" row is marked `INTEGRATE` and lists only `aft_formula / aft_formula_summary`, without a parallel `OPT-OUT` row explaining the missing `_formula_predict` variants — unlike every other scoping decision in the same document, which the project's own gate rule requires ("the coverage gate accepts only INTEGRATE / OPT-OUT rows"). The regression skill cheat-sheet (`plugins/polars-statistics/skills/polars-statistics-regression/SKILL.md`) does note "no aft_formula_predict exists — use aft_predict_* directly", so the omission is not undiscoverable, but the authoritative coverage-tracking artifact doesn't record the reasoning, leaving it looking like an oversight rather than a decision.
**Fix:** Either add the four `aft_formula_predict_*` wrappers (trivial given the existing `_aft_predict` helper and `penalized_glm_formula_predict` precedent), or add an explicit `OPT-OUT` row to COVERAGE.md explaining why AFT's formula-predict variants were dropped while `penalized_glm`'s were kept.

### WR-02: `penalized_glm_predict`/`penalized_glm_formula_predict`'s `type` parameter shadows the builtin `type`

**File:** `python/polars_statistics/exprs/regression.py:4553` (`def penalized_glm_predict(..., type: Literal["response", "link"] = "response", ...)`) and its formula wrapper
**Issue:** Every other predict expression in this file uses `interval`/`predict_type`-style names; `penalized_glm_predict` and `penalized_glm_formula_predict` name the parameter `type`, shadowing the Python builtin within the function body (and in any `**kwargs`-passthrough call site). Not a functional bug here (the builtin isn't used inside the function), but it's an inconsistent, easily-misused name versus the rest of the module's conventions, and static analysis/linters commonly flag `type` as a shadowed builtin.
**Fix:** Rename to `predict_type` (matching the Rust `PenalizedGlmKwargs.predict_type` field name it maps to 1:1) for both the plain and formula variants.

## Info

### IN-01: `offset=None` → `pl.lit(0.0, dtype=pl.Float64)` boilerplate duplicated three times

**File:** `python/polars_statistics/exprs/regression.py` — `penalized_glm`, `penalized_glm_summary`, `penalized_glm_predict`
**Issue:** The 5-line `if offset is None: ... elif isinstance(offset, str): ... else: ...` block normalizing the offset expression is repeated verbatim in all three entry points. Pure duplication; any future change (e.g. validating non-Float64-castable offsets) has to be made in three places.
**Fix:** Factor into a small `_normalize_offset(offset) -> pl.Expr` helper alongside `_normalize_priors`.

### IN-02: `n_rows` consistency relies on `inputs[0].len()` without an explicit shape check against `event`/`x` columns

**File:** `src/expressions/aft.rs:538` (`aft_predict_impl`) and `src/expressions/penalized_glm.rs:795` (`penalized_glm_predict_fit`)
**Issue:** `n_rows`/`n` is taken from `inputs[0].len()` and then indexed into `inputs[1]`, `inputs[2..]` assuming identical length, matching the existing convention elsewhere in the codebase (Polars guarantees same-length columns within one `select`/`group_by` call, so this isn't exploitable from normal usage) — flagged only because the four new `aft_predict_*` functions reuse this pattern without a comment noting the invariant, unlike `build_xy_with_null_policy`'s callers elsewhere which rely on Polars' own column-length guarantee implicitly documented at the call site. No fix required; noted for completeness since the reviewed functions are the first AFT-side callers of this reuse pattern.
