# Phase 16.1: Upstream Crate Refresh - Research

**Researched:** 2026-10-08
**Domain:** Rust crate upgrade (anofox-statistics, anofox-regression) + Polars/PyO3 API-surface exposure
**Confidence:** HIGH

## Summary

This phase bumps two backing Rust crates and exposes their new API surface through the
existing `#[polars_expr]` / PyModel layering. The upgrade is mechanically simple (`cargo
update -p` only; zero source-breaking changes confirmed by the orchestrator and by reading
both crates' lockstep `lib.rs` re-export lists). The real work is in three places: (1)
updating two pytest assertions that currently encode a pre-fix number that upstream has
now made correctly NaN (Tweedie `var_power=1.5` AIC/BIC), (2) wiring ~17 new upstream
functions/builder options into the expression and PyModel layers using patterns that
already exist verbatim in this codebase for near-identical problems (optional inference
fields are **already** handled via `Option<T>` + NaN-fill at every call site that was
inspected), and (3) propagating the new surface into `.pyi` stubs, mkdocs pages, the
CHANGELOG, and the five `SKILL.md` cheat-sheets bundled as the Phase 13-15 plugin.

Critically, **no code in this repository currently panics or `.unwrap()`s on the
`Option<T>` inference fields that Ridge/Huber/RANSAC/NegBin return** — every expression
site found (`ols_summary_fit`, `ridge_summary_fit`, `negative_binomial_summary_fit`, …)
already does `if let Some(ref se) = result.std_errors { .. } else { fill NaN }`, and every
PyModel getter inspected for OLS/NegBin already returns `Option<Bound<PyArray1<f64>>>`.
This means the Ridge-λ>0-now-returns-`None`-inference behaviour change (upstream #37) is
very likely **already safe at the expression layer** with no code change required — only a
new pytest assertion is needed to lock in the NaN/None expectation. Huber and RANSAC are
the two models whose PyModel wrappers do **not** yet call `.compute_inference(true)` at
all (point estimates only) — these need new builder wiring, not Option-safety fixes.

**Primary recommendation:** Treat this phase as four small, independently-committable
waves — (1) bump + fix the two Tweedie test assertions + lock a Ridge-λ>0-is-None
regression test, (2) new `anofox-statistics` surface (effect sizes, Jarque-Bera, bootstrap
CI, conditional Fisher, `conf_level` variants), (3) new `anofox-regression` surface (GLMM
Wald inference, Huber/RANSAC inference, NegBin dispersion, RLS `initial_p_diagonal`), (4)
stubs/docs/CHANGELOG/skills. Each wave follows an **exact existing analog already read this
session** — no new architectural pattern is required anywhere in this phase.

## Project Constraints (from CLAUDE.md)

- Tech stack: Rust 2021 + PyO3 0.26 + Polars 0.52; new API must follow the existing
  `#[polars_expr]` / PyModel patterns and output-struct schemas.
- Validation: new tests validated against R where the crates supply references.
- CI gates: `cargo clippy --all-targets -- -D warnings`, `cargo fmt --all -- --check`,
  ruff (line length 100, py39 target, ignore E501), full pytest — all must stay green.
- Compatibility: maintain Python 3.9-3.12 across Linux/macOS/Windows wheels.
- Release: production PyPI via existing GH Actions OIDC pipeline (out of scope for this
  phase — Phase 17 ships the release).
- Naming: snake_case Rust functions/fields, `PyXxx` PyO3 struct names, `#[getter]` for
  read-only Python properties, `Option<T>` fields map to `Option<Bound<PyArrayN<f64>>>` /
  `Option<f64>` Python-side (never `.unwrap()` across the FFI boundary).
- Module design: `src/expressions/mod.rs` and `src/pymodels/mod.rs` re-export new public
  items automatically via `pub use module::*` wildcards — no registry file to edit for new
  free functions; new `#[pyclass]` methods need no `m.add_class` change (classes already
  registered in `src/lib.rs`'s `#[pymodule]` block); genuinely new `#[polars_expr]`
  functions are discovered by `register_plugin_function(function_name=...)` string match
  from the Python side, so no Rust-side registry edit is needed there either — only the
  Python builder's `function_name=` string must match the new Rust fn name.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|--------------|-----|
| Bootstrap CI with an arbitrary user statistic | A Python-callback-into-Rust bridge (PyO3 `Py<PyAny>` closure called from inside the Rust bootstrap loop) | A fixed `Literal["mean","median","std",...]` dispatch that calls the crate's own `bootstrap_ci`/`bootstrap_mean_ci` with a matching Rust closure | The crate's `bootstrap_ci<F: Fn(&[f64]) -> f64>` is generic over a **native Rust** closure; there is no existing precedent anywhere in this codebase for calling back into Python from inside a `#[polars_expr]` function, and doing so would add a GIL-reentrancy hazard inside Polars' multi-threaded group_by execution — a correctness and deadlock risk, not just an ergonomics one. |
| Nesting `FittedOls` (RANSAC's `inlier_fit()`) as a Python object | A generic `PyFittedOls` wrapper class that holds a borrowed/owned `FittedOls` and re-exposes all of OLS's getters | A handful of delegating methods (`inlier_coefficients()`, `inlier_r_squared()`, …) directly on `PyRANSAC` | `FittedOls` is not `Clone`-cheap-wrapped as a standalone pyclass anywhere in this codebase; inventing that pattern for one accessor is disproportionate. | Conditional Fisher's exact CI root-finding | Reimplementing the noncentral-hypergeometric bisection in the FFI layer | Call `fisher_exact_conditional` directly — it is a pure function already validated to ~1e-4 against R | The crate already does the hard numerical work (bisection to machine precision vs R's `uniroot` at ~1e-4 tolerance) — the FFI layer is pure marshaling. |

**Key insight:** every "new capability" in this phase is a thin marshaling problem, not a
math problem — the hard numerics are already implemented and R-validated upstream. The one
place genuine engineering judgment is needed is bootstrap_ci's generic-closure signature,
which cannot cross the FFI boundary as-is and needs an explicit, documented scope
reduction (fixed statistic set) rather than a heroic bridge.

## Common Pitfalls

### Pitfall 1: Assuming `Option<T>` inference fields need defensive code that doesn't already exist
**What goes wrong:** Spending a task "fixing" Ridge/Huber/NegBin's Option-handling for the
λ>0-returns-None behaviour change, when the expression layer already handles it.
**Why it happens:** The roadmap's phrasing ("will None now produce errors/panics (unwrap)
in our wrappers for λ>0 Ridge?") reads like an open risk.
**How to avoid:** This session confirmed by reading the actual code that `ols_summary_fit`,
`ridge_summary_fit`, `negative_binomial_summary_fit`, and the PyO3 getters on `PyOLS`/
`PyNegativeBinomial` all already use `if let Some(...) else NaN-fill` / `Option<Bound<...>>`
— **zero `.unwrap()` calls on `std_errors`/`t_statistics`/`p_values`/`intercept_std_error`
were found** in a targeted grep of `regression.rs` and the `py_*.rs` files read this
session. The actual work is a **new pytest assertion**, not a source fix.
**Warning signs:** If a planned task says "add null-safety to Ridge inference", that task
is likely redundant — verify first with `grep -n "std_errors" src/pymodels/py_ridge.rs` (at
research time, this returns **zero** getter-level matches — PyRidge exposes no direct SE
getters at all, only the separately-computed `hc_inference()`).

### Pitfall 2: Breaking the `#[polars_expr]` input-index contract silently
**What goes wrong:** Adding a new scalar kwarg (e.g. `conf_level`, `estimate_dispersion`,
`initial_p_diagonal`) to only one side (Python builder or Rust `_fit` function) of a
function pair, or to only one of several expressions that share an input-index convention
(e.g. RLS's `rls_fit`/`rls_summary_fit`/`rls_predict_fit` trio).
**Why it happens:** Each `_fit` function hand-indexes `inputs[N]` with no compile-time
check that the Python side sends N+1 args in the same order — a silent off-by-one produces
wrong results, not a crash (e.g. reading `with_intercept` as a Float64 would error loudly,
but reading `lambda` where `conf_level` was intended produces silently wrong — but
plausible — numbers).
**How to avoid:** Change the Python builder and the Rust `_fit` function **in the same
commit**, and immediately write/run a pytest that passes a non-default value for the new
kwarg and asserts the result differs from the default (not just "doesn't crash").
**Warning signs:** A new kwarg that is accepted by the Python function signature but never
appears in a `pl.lit(...)` inside its `args=[...]` list — this compiles and runs but
silently ignores the kwarg.

### Pitfall 3: Treating "doesn't fail now" as "value is unaffected" (UPST-02's core risk)
**What goes wrong:** Concluding the 0.4.3/0.4.4/0.5.14/0.5.15 numeric-value changes
(Shapiro-Wilk n≤11, Kendall ties, binomial/proportion/Fisher intervals, exact Mann-Whitney)
need no test updates because the full suite passes post-bump.
**Why it happens:** A loose `pytest.approx` tolerance, or an assertion that only checks
shape/sign/finiteness rather than a precise reference value, will keep passing even though
the underlying number silently changed to the new, more-correct value.
**How to avoid:** Per the Runtime/Behaviour-Change Inventory above, grep each affected test
file for literal float assertions and manually cross-check against the changelog's stated
fix magnitude; do not rely solely on "pytest is green."
**Warning signs:** A test asserting `result.p_value < 0.05` (direction/threshold-only) for
a function whose p-value the changelog says changed — this kind of assertion survives both
the old and new value and gives false confidence.

### Pitfall 4: Non-finite input handling (0.4.4 #17) silently changes error surface shape
**What goes wrong:** Upstream functions that previously panicked on NaN/Inf (crashing the
whole Python process via a Rust panic across the FFy boundary — already a latent bug in
0.4.2) now return a typed `Err` instead. If the `#[polars_expr]` call site already does
`match result { Ok(..) => .., Err(_) => nan_output() }` (the universal pattern in this
codebase), this is a strict improvement with zero code change. But if a PyModel's `fit()`
propagates the error as a `PyValueError` (also the universal pattern, confirmed in every
`py_*.rs` file read this session), behaviour changes from "process crash" to "catchable
Python exception" — which is desirable, but is a **user-visible behaviour change** worth
a CHANGELOG line, and an opportunity to add the "don't crash on NaN/Inf" regression tests
recommended in the inventory table above.
**How to avoid:** Add the NaN/Inf regression tests explicitly; don't assume "it already
doesn't panic" is equivalent to "it is tested not to panic."
