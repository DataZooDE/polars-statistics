## Decisions Made

- `PyWLS`/`PyRidge`'s `fitted` field changed from `Option<Box<dyn FittedRegressor + Send + Sync>>` to the concrete `Option<FittedWls>`/`Option<FittedRidge>`. The plan's action items for Task 3 assumed `fitted.variance_factor()`/`.leverage_new()` were directly callable on the stored value, but those are inherent methods on the concrete fitted structs, not part of the `FittedRegressor` trait, so a boxed trait object cannot reach them. Verified both solvers' `Regressor::Fitted` associated type is already the concrete struct in the upstream crate (`fit()` and `fit_from_accumulator()` both produce exactly one concrete type each), so this is a pure type-narrowing refactor: every trait method used elsewhere (`predict`/`result`/`coefficients`/`intercept`/`score`) resolves identically through the already-imported trait.
- Fixed the Huber MASS::rlm test's p-value assertion from `0.0 < p < 1.0` to `0.0 <= p < 1.0`: this fixture's huge t-statistic (~66.7, df=18) underflows the two-sided p-value to exactly `0.0` in f64 — numerically correct, not a bug. The upstream crate's own reference test does not assert `p_values` at all, confirming the plan's "p_values in (0, 1)" prose was an unverified assumption rather than an established fact.
- `WLS.hc_inference`'s comment and `NotImplementedError` message (both claiming the weight vector was unreachable through `Box<dyn FittedRegressor>`) were corrected to reflect that `fitted.weights()` is now reachable after the field-type refactor — the method still intentionally raises because implementing the weight-aware HC sandwich itself is out of this plan's scope, but the stated reason no longer misrepresents why.
- `MomentAccumulator.push_row` requires a C-contiguous 1-D array; `polars.DataFrame.to_numpy()` row-slices (`X[i]`) are not guaranteed contiguous, so the moments-fit test wraps each row in `np.ascontiguousarray(...)` (matching the existing error message's own suggested workaround).

## Deviations from Plan

### Auto-fixed Issues

**1. [Rule 3 - Blocking] `PyWLS`/`PyRidge.fitted` boxed trait object could not reach `variance_factor()`/`leverage_new()`**
- **Found during:** Task 3, before writing `py_wls.rs`/`py_ridge.rs` edits (confirmed via source read that `variance_factor`/`leverage_new` are inherent `impl FittedWls`/`impl FittedRidge` methods, not on the `FittedRegressor` trait)
- **Issue:** `fitted: Option<Box<dyn FittedRegressor + Send + Sync>>` cannot call inherent (non-trait) methods without downcasting, and `FittedRegressor` has no `Any`/downcast support
- **Fix:** Changed both fields to the concrete `Option<FittedWls>`/`Option<FittedRidge>` (matching each solver's actual `Regressor::Fitted` associated type) and updated the two assignment sites per struct (`Some(Box::new(fitted))` -> `Some(fitted)`)
- **Files modified:** `src/pymodels/py_wls.rs`, `src/pymodels/py_ridge.rs`
- **Verification:** `cargo clippy --all-targets -- -D warnings` clean; full `uv run pytest tests/ -q` — 994 passed, 0 failed (no regression in any existing WLS/Ridge test)
- **Committed in:** `644cbc7` (Task 3 commit)

**2. [Rule 1 - Bug] Huber MASS reference test asserted a strictly-positive p-value that underflows to exactly 0.0**
- **Found during:** Task 1's first `pytest -k huber` run
- **Issue:** `assert 0.0 < m.p_values[0] < 1.0` failed — the fixture's t-statistic (~66.68, df=18) produces a p-value that underflows to exactly `0.0` in f64 (astronomically significant, not a representable positive float)
