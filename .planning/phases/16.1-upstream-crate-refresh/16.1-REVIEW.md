# Phase 16.1: Code Review Report

**Reviewed:** 2026-10-09T09:46:00Z
**Depth:** standard
**Files Reviewed:** 69
**Status:** issues_found

## Summary

This phase refreshes `anofox-statistics` (0.4.2 → 0.4.6) and `anofox-regression` (0.5.13 →
0.5.16) and exposes the new API surface those crates provide: effect sizes (`cohens_d`,
`rank_biserial` family), Jarque-Bera, percentile bootstrap CIs, `fisher_exact_conditional`,
`conf_level` on the existing proportion/Fisher tests, Huber/RANSAC inference getters,
`RANSAC.inlier_fit()`, `variance_factor()`/`leverage_new()` on OLS/WLS/Ridge,
`NegativeBinomial.estimate_dispersion`, `RLS.initial_p_diagonal`, `TheilSen.univariate_pairwise`,
and GLMM Wald inference (`z_values`/`p_values`/`conf_int`).

I read every file in the required list, traced the kwargs plumbing from each Python builder
through to its `#[polars_expr]` Rust shim, diffed `src/expressions/output_types.rs` against
every call site to check struct-field order, and cross-referenced the `.pyi` stub diff against
the Rust `#[pyo3]` diff field-by-field. I then built and ran the project's own `.venv` (compiled
from this exact source tree) and exercised: the full Python test suite relevant to this phase
(532 tests, all green), every runnable code example in the changed docs/SKILL.md files, and
several numeric spot-checks against the R references the PLAN/CHANGELOG cite (Cohen's d,
rank-biserial, Jarque-Bera, Fisher conditional odds ratio/CI, Kendall's tau tie-correction,
GLMM Wald `conf_int`). All of it reproduced the documented values. I also attempted
`cargo test --release --test rust_api`, which uncovered the CI gap described in WR-03 below.

No BLOCKER-level defects (incorrect behavior, security issue, or data-loss risk) were found.
The engineering here is unusually careful: every new `*_fit`/`*_fit_with` has an explicit
"old arity == new default" regression test, every inference getter has an
`Option<...>`-returning signature wired to the `compute_inference` flag rather than a
possibly-wrong default, and every behavior change inherited from the upstream crates is called
out in the docstrings, CHANGELOG, and validation tables. The warnings below are about
silent-semantics risk, output-schema visibility, and a test-suite blind spot — not incorrect
arithmetic.

## Warnings

### WR-01: `RANSAC.r_squared`/`.n_observations` silently changed meaning with no runtime signal

**File:** `src/pymodels/py_ransac.rs:217-227` (getter bodies unchanged; semantics changed by
the `anofox-regression` 0.5.14 bump)
**Issue:** Pre-existing, already-shipped public getters `RANSAC.r_squared` and
`RANSAC.n_observations` (plus the newly-exposed `adj_r_squared`/`mse`/`rmse`/`f_statistic`/
`aic`/`bic`/`log_likelihood`) now describe the **inlier-only** OLS fit instead of the whole
sample — `n_observations` now equals `n_inliers`, not the original row count. This is
documented thoroughly (docstrings, CHANGELOG, `docs/api/classes/linear.md`), but nothing fires
at runtime: existing user code that read `model.r_squared` or `model.n_observations` before
this upgrade will silently get a different, differently-scoped number after upgrading, with no
exception and no warning. This is inconsistent with the project's own established pattern for
breaking parameter changes — `with_intercept` → `add_intercept` emits a `PyFutureWarning`
(`src/pymodels/errors.rs:65-83`) — but no equivalent signal exists for this getter-semantics
change.
**Fix:** Either emit a one-time `FutureWarning` the first time `r_squared`/`n_observations` is
read on a `RANSAC` instance (mirroring `resolve_intercept`'s pattern), or at minimum surface
this prominently at the top of the release notes/migration guide (not just inside the
CHANGELOG's "Behaviour changes" prose) so users upgrading `anofox-regression` transitively via
a `polars-statistics` version bump don't silently get different numbers in dashboards/reports
built against the old semantics.

### WR-02: `pl_fisher_exact`'s output struct grew from 2 to 4 fields for an already-shipped expression

**File:** `src/expressions/categorical.rs:414` (`#[polars_expr(output_type_func=fisher_output_dtype)]`
replacing `stats_output_dtype`); `src/expressions/output_types.rs:48-66`
**Issue:** `pl_fisher_exact` (already public in 0.7.0) now returns
`struct{statistic, p_value, ci_lower, ci_upper}` instead of `struct{statistic, p_value}`. This
is additive (the two pre-existing fields keep their name, order, and value — confirmed by
`tests/rust_api.rs`'s explicit `n_fields == 4` assertion and the CHANGELOG's "Changed" entry),
so it complies with the project's additive-only convention for output structs. Flagging it
anyway per the explicit review brief: any downstream consumer that does positional/tuple
unpacking of the struct, or asserts an exact schema (`len(fields) == 2`, `df.schema ==
Schema({...})`), will break on upgrade even though field *names* didn't change.
**Fix:** No code change needed — this is the one output-struct growth in the diff and it's
correctly additive. Consider calling it out by name (not just "Woolf interval added") in the
top-level `## New in 0.8.0` section of `docs/API_REFERENCE.md`, since it's the only
backward-compatibility-relevant schema change in an otherwise purely-additive release.

### WR-03: `tests/rust_api.rs` cannot link in the project's default feature set — the new Rust-level regression tests never actually run in CI

**File:** `tests/rust_api.rs` (whole file); `Cargo.toml:23` (`pyo3 = { ..., features =
["abi3-py39", "extension-module"] }`, enabled by the default `python` feature);
`.github/workflows/ci.yml` (no `cargo test` step anywhere)
**Issue:** This diff adds substantial new Rust-level regression coverage to
`tests/rust_api.rs` — explicit old-arity/new-arity equivalence checks for
`binom_test_fit`/`prop_test_one_fit`/`prop_test_two_fit`/`fisher_exact_fit`, `rls_fit` ==
`rls_fit_with(default)`, `negative_binomial_fit` == `negative_binomial_fit_with(default)`, and
a whole new `effect_size_and_resampling_fits` test with R-pinned numeric assertions. I tried to
run it (`cargo test --release --test rust_api`) and the build fails at the link step:
```
rust-lld: error: undefined symbol: PyGILState_Ensure
rust-lld: error: undefined symbol: PyErr_Fetch
... (9 more undefined Python C-API symbols)
error: could not compile `polars-statistics` (test "rust_api") due to 1 previous error
```
This happens because `pyo3`'s `extension-module` feature is unconditionally pulled in by the
default `python` feature (`Cargo.toml:17-23`), and `extension-module` deliberately omits
linking against `libpython` (correct for a cdylib loaded by `dlopen` from a running Python
process, wrong for a standalone test binary that needs real symbol resolution). I confirmed
`cargo clippy --all-targets` (what CI's `lint` job actually runs) exits 0 on the same tree —
clippy type-checks but does not link, so it never hits this error. I also grepped
`.github/workflows/ci.yml` end-to-end: there is no `cargo test` step at all, only
`cargo clippy --all-targets` and the Python/maturin pipeline. `cargo test --release --test
rust_api --no-default-features` does link successfully (confirmed; takes a full from-scratch
release build since the default-feature build artifacts aren't reusable with a different
feature set).
**Fix:** Either (a) add a CI job that runs `cargo test --no-default-features` (cheap: the rlib
build without the `python` feature doesn't need maturin/numpy/pyo3 at all) so
`tests/rust_api.rs` actually executes on every PR, or (b) document the correct invocation in
`CONTRIBUTING`/README's dev-workflow section so a human running `cargo test` locally doesn't
hit this silently (right now they get a linker wall of text, not a helpful message), or (c)
restructure so `tests/rust_api.rs` is gated to run under `--no-default-features` explicitly
(e.g. a `#[cfg(not(feature = "python"))]` guard plus a dedicated CI matrix entry). Today, the
careful backward-compatibility tests added in this very diff provide no actual safety net —
a regression in any `*_fit` function's arithmetic would not be caught by CI.

## Info

### IN-01: Missing blank line before `__repr__` in two of the four PyModel files touched

**File:** `src/pymodels/py_huber.rs:195-196`, `src/pymodels/py_ransac.rs:533-534`
**Issue:** In `py_huber.rs` and `py_ransac.rs`, the new `intercept_conf_interval`/`inlier_fit`
getter's closing `}` is immediately followed by the `/// Informative repr...` doc comment with
no blank line, while the equivalent spot in `py_ridge.rs:409-411`, `py_wls.rs:280-282`, and
`py_ols.rs:591-593` (all touched in the same commit) keeps the blank line. `cargo fmt --check`
does not flag this (confirmed), so it's purely a readability/consistency nit, not a build gate.
**Fix:** Add the blank line in both files for consistency with the rest of the diff:
```rust
        Ok(fitted.result().intercept_conf_interval)
    }

    /// Informative repr: class name plus key state; never panics if unfitted.
```

### IN-02: `FIXTURE_SHA256_PREFIX` holds the full digest and is compared with exact equality, not a prefix check

**File:** `tests/test_wilcoxon_mcnemar_parity.py:35`
**Issue:** `FIXTURE_SHA256_PREFIX = "e51fd41b79d5e43274cfe86378e71395b2a96461347294add8e425c52863c296"`
is 64 hex characters — the entire SHA-256 digest, not a prefix — and
`test_hodges_lehmann_fixture_integrity` compares it with `==`, not `.startswith(...)`. The test
is correct and currently passing (I verified the hash matches
`tests/fixtures/wilcox_ci_reference.csv` byte-for-byte), so this doesn't affect reliability;
the name is just misleading for the next person who reads it expecting a short prefix check.
**Fix:** Rename to `FIXTURE_SHA256` (drop `_PREFIX`), or truncate the constant to an actual
short prefix and change the assertion to `digest.startswith(FIXTURE_SHA256_PREFIX)` if a
partial check was the original intent.

### IN-03: `WLS.hc_inference` still raises `NotImplementedError` even though the data needed to implement it is now in hand

**File:** `src/pymodels/py_wls.rs:36-62`
**Issue:** This diff changes `PyWLS.fitted` from `Option<Box<dyn FittedRegressor + Send +
Sync>>` to `Option<FittedWls>` specifically so the weight vector is reachable
(`fitted.weights()`), per the updated comment at line 44-50. `hc_inference` still immediately
returns `NotImplementedError`, with the comment now reading "computing this sandwich is out of
this plan's scope — not implemented yet." That's a legitimate, explicitly-documented scope cut
(and the previous code's blocker — an un-downcastable `Box<dyn FittedRegressor>` — is exactly
what motivated the type change) but every other deferred-scope comment in this diff cites a
tracking issue number (`#37`, `#42`, `#49`, `#50`); this one doesn't, which makes it harder for
a future contributor to know where to pick this up.
**Fix:** Reference the tracking issue/plan item for the WLS HC-sandwich follow-up the same way
the other deferred items do, e.g. `// TODO(#NN): wire up the weight-aware sandwich now that
fitted.weights() is reachable.`

### IN-04: "Bit-identical" invariant between `bootstrap_ci("mean", ...)` and `bootstrap_mean_ci(block_length=0, ...)` is enforced only by a comment + one test, not by shared code

**File:** `src/expressions/resampling.rs:117-124`
**Issue:** `bootstrap_ci_fit`'s `"mean"` arm hand-rolls `|s: &[f64]| s.iter().sum::<f64>() /
s.len() as f64` and relies on a comment ("Exactly upstream's own mean closure ... so this arm is
bit-identical to bootstrap_mean_ci(block_length=0)") rather than calling a single shared helper.
The guarantee is currently backed by one regression test
(`tests/test_jarque_bera_bootstrap.py::test_mean_matches_bootstrap_mean_ci`), which is good, but
a future edit to either closure (e.g. switching to a more numerically-stable mean, like Welford's
algorithm, in just one of the two places) would silently break the parity claim in the docstring
and SKILL.md without any compiler-level signal — only the one test would catch it, and only if
run.
**Fix:** Low priority given the existing test coverage; if touched again, consider extracting
the mean closure into a single `const`/`fn` used by both `bootstrap_ci_fit`'s `"mean"` arm and
documented as literally the same expression `bootstrap_mean_ci` uses, to make the invariant
structural rather than comment-enforced.
