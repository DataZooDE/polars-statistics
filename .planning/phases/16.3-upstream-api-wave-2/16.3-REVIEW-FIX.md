## Fixed Issues

### CR-01: `ps.augment(model="negative_binomial", theta=...)` silently ignores the fixed theta

**Files modified:** `src/expressions/regression.rs`, `tests/test_augment.py`
**Commit:** `b26b5ee`
**Applied fix:** In `augment_fit`'s `"negative_binomial"` dispatch arm, added
`.estimate_theta(false)` alongside `.theta(t)` when the user supplies a fixed
`theta`, mirroring the correct fixed-theta handling already used by the GLMM
`nb_theta` path. Without this call, `NegativeBinomialRegressorBuilder`'s
default `estimate_theta=true` silently overwrote the user's `theta` with the
ML estimate before the fit even started.

Strengthened `test_negative_binomial_fixed_theta_matches_estimated` to use a
fixed `theta=2.0` (far from the data's ML estimate, `ref.NB_THETA` ~= 9.94):
it now asserts the augment fitted values match a truly-fixed-theta
`NegativeBinomial(theta=2.0, estimate_theta=False)` reference fit at
`rel=1e-8`, and that `std_residual`/`cooks_d` (which depend on the dispersion,
unlike `fitted`) differ measurably from the fully-estimated-theta fit — the
previous version could not distinguish "theta correctly fixed" from "theta
silently ignored".

**Additional checks performed (per fix-scope instructions):**
- `src/pymodels/py_negative_binomial.rs` (`PyNegativeBinomial::fit`/`augment`):
  no fix needed. This PyModel's constructor already exposes `theta` and
  `estimate_theta` as two independent, explicit parameters (`estimate_theta`
  defaults to `true` but the user must opt into a truly-fixed theta by also
  passing `estimate_theta=False`, same as the upstream builder's own
  contract) — there is no silent-override bug here because nothing is
  inferred from `theta` alone. `.augment()` itself only reads the
  already-fitted model and does not refit, so it is unaffected either way.
- **Possible related issue found but out of the stated fix scope (not fixed
  here, flagged for the user):** `negative_binomial_fit_with` and
  `negative_binomial_summary_fit_with` (the `ps.negative_binomial` /
  `ps.negative_binomial_summary` expressions, `src/expressions/regression.rs`
  lines ~2665-2673 and ~3975-3983) have the same `builder.theta(t)` without
  `.estimate_theta(false)` pattern as the CR-01 bug. The existing regression
  tests for these two expressions (`tests/test_negbin_rls_options.py`,
  `tests/test_penalized_glm.py`) happen not to catch it because the fixed
  `theta` values used (`THETA`/`ref.NB_THETA`) are each dataset's own ML
  estimate, so "fixed" and "estimated" converge to the same value regardless
  of whether `estimate_theta` is actually set to `false`. This was not a
  CR-01/REVIEW.md finding and was left untouched to keep this fix set scoped
  to the four documented findings; recommend filing it as a new finding in a
  follow-up review.

### WR-01: `ps.augment()`'s `weights` docstring contradicts its own code for `model="wls"`

**Files modified:** `python/polars_statistics/exprs/regression.py`
**Commit:** `e81729a`
**Applied fix:** Rewrote the `weights` parameter docstring to state the
actual, tested behavior: required with `model="wls"` (`ValueError` if

`docs/api/regression/diagnostics.md`'s existing description was already
accurate and needed no change.

### WR-02: A single non-finite value silently discards an entire post-hoc comparison

**Files modified:** `src/expressions/posthoc.rs`, `python/polars_statistics/exprs/posthoc.py`, `docs/api/tests/posthoc.md`, `tests/test_posthoc.py`
**Commit:** `6410daa`
**Applied fix:** Changed `long_format`'s row filter from `!v.is_nan()` to
`v.is_finite()`, so a `+Inf`/`-Inf` value is dropped like a null/NaN value
instead of reaching upstream `ensure_finite` and emptying the entire
pairwise-comparison output. Documented the non-finite row-drop behavior in
the `ps.tukey_hsd`/`ps.pairwise_t_test`/`ps.dunn_test` Python docstrings, the
corresponding Rust `*_fit` doc comments, and the shared note on
`docs/api/tests/posthoc.md`. Added `test_pairwise_inf_row_dropped`, which
confirms a single `+Inf`/`-Inf` row no longer empties the result for all
three functions and that the surviving rows match the clean-data baseline.

## Follow-up FU-01

**Out-of-scope observation (CR-01, above) confirmed and fixed as a follow-up.**

**Bug:** `ps.negative_binomial("y", "x", theta=t)` and `ps.negative_binomial_summary(...,
theta=t)` silently re-estimated `theta` instead of holding it fixed —
reproduced directly: with a dataset whose ML theta differs materially from
`t`, both `theta=0.5` and `theta=10.0` returned coefficients identical (to
~1e-9) to the fully-estimated fit, while `NegativeBinomial(theta=t,
estimate_theta=False).fit(...)` (the PyModel path, unaffected) gave visibly
different coefficients for the same data and `t`.

**Files modified:** `src/expressions/regression.rs`, `tests/test_negbin_rls_options.py`, `CHANGELOG.md`
**Commit:** (see `git log --oneline -3` for this follow-up)
**Applied fix:** In `negative_binomial_fit_with` (~line 2665, backs
`ps.negative_binomial`) and `negative_binomial_summary_fit_with` (~line 3984,
backs `ps.negative_binomial_summary`), changed:

```rust
if let Some(t) = theta {
    builder = builder.theta(t);
} else {
    builder = builder.estimate_theta(true);
}
```

to:

```rust
if let Some(t) = theta {
    builder = builder.theta(t).estimate_theta(false);
} else {
    builder = builder.estimate_theta(true);
}
```

matching the pattern already correct in `augment_fit`'s `"negative_binomial"`
arm (line 3133, from CR-01) — `NegativeBinomialRegressorBuilder::theta()`
only sets the starting/fixed value and never touches `estimate_theta` (default
`true`), so a fixed `theta` must always be paired with an explicit
`estimate_theta(false)` call or it is silently overwritten by the ML
estimate during `.fit()`.

**Paths checked and found NOT to need this fix** (grepped every `.theta(`
call site in `src/expressions/` and every `NegativeBinomialRegressor::builder()`
construction in `src/`):

- `augment_fit` (`"negative_binomial"` arm, line 3133) — already fixed by
  CR-01.
- `negative_binomial_predict_fit_with` (line 5335, backs
  `ps.negative_binomial_predict`) — this expression's positional input
  contract has no `theta` input at all (confirmed against both the Rust
  function signature and the Python wrapper
  `python/polars_statistics/exprs/regression.py::negative_binomial_predict`,
  which has no `theta` parameter); a fixed theta can never reach this
  builder, so there is nothing to fix. `estimate_theta` is always left at
  its builder default (`true`), which is correct here since the point and
  interval predictions always use the model's own estimated theta.
- `src/pymodels/py_negative_binomial.rs` (`PyNegativeBinomial::fit`) — not
  affected, as already noted under CR-01: `estimate_theta` is an independent,
  explicit constructor parameter the user must set themselves; nothing is
  inferred from `theta` alone.
- `src/expressions/penalized_glm.rs` (the `ps.penalized_glm` /
  `ps.penalized_glm_formula` family-generic GLM engine, which also supports
  `family="negative_binomial"` with a `theta` kwarg) — a structurally
  different code path: it passes `theta: Option<f64>` directly into
  `PenalizedGlmFamily::NegativeBinomial { theta }` rather than through the
  `NegativeBinomialRegressorBuilder::theta()`/`estimate_theta()` pair, so
  there is no separate flag for a fixed `theta` to silently fail to set.
  Out of scope for this follow-up (not part of the `ps.negative_binomial`
  surface the bug report named) and not affected by the same bug mechanism.
- `ps.negative_binomial_formula` — delegates straight to `negative_binomial()`
  (confirmed in `python/polars_statistics/exprs/regression.py`), so it is
  covered by the `negative_binomial_fit_with` fix with no separate change
  needed.

**Output struct `theta` field:** the orchestrator's reproduction noted the
output's `theta` field printed `None`. Checked `glm_output_dtype` (the shared
output schema for Logistic/Poisson/NegBin/Tweedie/Probit/Cloglog): it has no
`theta` field at all — only `intercept`, `coefficients`, `aic`, `bic`,
`n_observations`. Per the additive-only schema rule, no field was added; the
`None` the orchestrator saw was simply a lookup against a key the struct has
never had, not a regression from this fix.

**Existing tests relying on the buggy behaviour:** none needed updating.
Grepped every `ps.negative_binomial*(..., theta=...)` call across `tests/`;
the only call sites passing an explicit `theta` were in
`tests/test_negbin_rls_options.py` (`THETA = 1.8294684732585813`, each
dataset's own `MASS::glm.nb` ML estimate) and `tests/test_glm_lambda.py`
(uses the PyModel directly with `estimate_theta=False` set explicitly,
already unaffected). As flagged in the original CR-01 note, `THETA` being the
dataset's own ML value means "fixed" and "estimated" converge to the same
answer regardless of whether `estimate_theta` was actually honored, so these
20 pre-existing assertions pass unchanged both before and after the fix —
they just never could have caught this bug. Added a new
`TestNegBinFixedThetaHonored` class (`tests/test_negbin_rls_options.py`) using
a simulated dataset (gamma-Poisson mixture, true `theta=3`, seed 7) whose ML
theta (~4.36) is far from the two fixed values exercised (`0.5`, `10.0`),
so a silently re-estimated theta is now distinguishable from a correctly
fixed one:

- `test_expression_matches_pymodel_fixed_theta` — `ps.negative_binomial(theta=t)`
  coefficients/intercept match `NegativeBinomial(theta=t,
  estimate_theta=False).fit(...)` at `rtol=1e-8`, for both `t`.
- `test_expression_fixed_theta_differs_from_estimated` — the fixed-theta fit
  differs from the fully-estimated fit by more than `1e-3` (would be
  numerically identical under the bug).
- `test_summary_matches_pymodel_fixed_theta` /
  `test_summary_fixed_theta_differs_from_estimated` — same two checks for
  `ps.negative_binomial_summary` (estimates and standard errors).
- `test_formula_matches_direct_call_fixed_theta` — `ps.negative_binomial_formula`
  with a fixed `theta` matches the direct `ps.negative_binomial` call.

**CHANGELOG.md:** added a `[Unreleased] > Fixed` bullet: "`ps.negative_binomial`
/ `ps.negative_binomial_summary` (and formula variants) now honour a fixed
`theta`; previously it was silently re-estimated."
